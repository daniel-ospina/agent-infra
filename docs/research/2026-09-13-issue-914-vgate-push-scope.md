- **2026-09-13T12:24:00** [canonical] **Architecture axis (Phase 1.5 — #914; Architecture=medium/high, UX=low, Ontology=low, deps=none).** `git diff A...B` is *defined* as `git diff $(git merge-base A B) B`; `git diff A..B` is a bare two-endpoint tree comparison. Git explicitly warns both are unrelated to `log`'s range notations ("diff is about comparing two endpoints, not ranges"). ⇒ 2-dot vs 3-dot answer **different questions**, not the same question with a different base. The push-range question is a *merge-base* question. Source: `man git-diff` (Git 2.50.1, local) + git-scm.com/docs/git-diff.

- **2026-09-13T12:24:01** [canonical] **★ `git diff <target>...HEAD` is the graph-derivable, non-reflog authored scope** — valid when there is **exactly one merge base** (`git-rebase(1)` names the `A...B` shortcut explicitly for exactly this). Because `git pull --rebase origin main` rewrites the branch so its merge base with the target *is* the new base, the 3-dot set is the authored delta with **zero reflog dependence**. **Named failure modes:** (1) **more than one merge base** (criss-cross — `git merge-base` documents "there can be more than one merge base"; the `A...B` shortcut is documented as valid only "if there is exactly one") ⇒ detect via `merge-base --all` count ≠ 1 and **fail closed**; (2) **no merge base** (shallow/partial clone, grafted, unrelated histories) ⇒ `fatal: no merge base`; (3) **wrong target** — must come from the PR/merge target or `refs/remotes/<remote>/HEAD`, **never** `branch.<name>.merge` (after `push -u` that names the branch itself); (4) 3-dot **omits remote-side-only loss** (the deliberate 2-dot property); (5) it does **not** answer "already landed upstream"; (6) it cannot see past a **rewound target** — the one case where reflog is genuinely required, usable only as a narrow fail-closed fallback (`git rebase --keep-base` is the documented graph-only counterpart). Source: `man git-rebase`, `man git-merge-base`, `man git-pull`.

- **2026-09-13T12:24:02** [pitfalls] **★ `git merge-base --fork-point` is unusable as this gate's basis, and it is *worse* than "reflog-dependent".** It "does not just look for the common ancestor … but also takes into account the **reflog of `<ref>`** to see if the history leading to `<commit>` forked from an **earlier incarnation** of the branch". The documentation is explicit that on reflog expiry it **fails rather than guesses**: "older reflog entries in your repository may be expired by git gc. If B0 no longer appears in the reflog … the `--fork-point` mode obviously cannot find it and **fails**, avoiding to give a random and useless result". Independently, it **misses the ordinary case**: "the remote-tracking branch you use the `--fork-point` mode with **must be the one your topic forked from its tip**. If you forked from an older commit than the tip, this mode would not find the fork point." ⇒ In agent/CI checkouts (fresh clone ⇒ empty or absent reflog; default `gc.reflogExpire` ~90 days) the mechanism is unavailable, and in the common "branch cut from an older commit" case it is wrong. Source: `man git-merge-base` "DISCUSSION ON FORK-POINT MODE" (Git 2.50.1) + lore.kernel.org/all/20240210-ez-merge-base-no-fork-point-v1-1-b3f82cdd3bee@gmail.com/T/ (upstream patch proposes falling back to plain `merge-base`).

- **2026-09-13T12:24:03** [canonical] **The house ceremony leaves no durable non-reflog record of the pre-rebase base.** `git rebase`/`git pull --rebase` are already fork-point-aware **by default** ("If `<upstream>` is not specified, the upstream configured in `branch.<name>.remote` and `branch.<name>.merge` options will be used and the **`--fork-point` option is assumed`"), and `ORIG_HEAD` is documented as **not guaranteed** to survive ("ORIG_HEAD is not guaranteed to still point to the previous branch tip"). ⇒ Any "where did this branch fork before the rebase?" mechanism is **necessarily** reflog-dependent. Source: `man git-rebase`, `man git-pull`, `man git-config`.

- **2026-09-13T12:24:04** [pitfalls] **`git rebase` silently omits commits whose patch already exists upstream** — "any commits in `HEAD` which introduce the same textual changes as a commit in `HEAD..<upstream>` are **omitted**". ⇒ **"authored scope empty" is a legal outcome**, not an anomaly; a gate must not false-positive on it. Source: `man git-rebase` DESCRIPTION.

- **2026-09-13T12:24:05** [canonical] **`@{push}` is NOT a fix for the trusted-base mis-anchor.** `@{push}` differs from `@{upstream}` **only in a triangular workflow** — "In a non-triangular workflow, `@{push}` is the same as `@{upstream}`". Since the mis-anchor is exactly `@{upstream}` resolving to the branch's own name, switching to `@{push}` changes nothing outside a triangular setup. Source: `man gitrevisions`, `man git-push -u`, `man git-config branch.<name>.merge`.

- **2026-09-13T12:24:06** [pitfalls] **`git patch-id` / `git cherry` cannot be a trust input.** patch-id is "nothing but a sum of SHA-1 of the file diffs … with line numbers ignored. As such, it's '**reasonably stable**', but at the same time also reasonably unique … The main usecase … is to look for **likely duplicate** commits." It is config/version-dependent (`--stable`/`--unstable`, `patchid.stable`, "Result is different from the value produced by git 1.9 and older"). Both directions fail: **false negatives** when the change landed with conflict resolution or other edits; **false positives** when different commits normalize to the same id (whitespace/line-number-insensitive). ⇒ A coincidentally-identical or reverted change would read as "landed" ⇒ **under-scope**. Source: `man git-patch-id`, `man git-cherry`.

- **2026-09-13T12:24:07** [canonical] **`git range-diff` answers a presentation question, not an authorization one.** It "first finds pairs of commits … Two commits are said to correspond when the diff between their patches … is **reasonably small** compared to the patches' size" (`--creation-factor` tuning, unmatched commits inserted after ancestors). ⇒ similarity heuristic for interdiff review, **not** a per-path authorization oracle. Source: `man git-range-diff`, git-scm.com/docs/git-range-diff.

- **2026-09-13T12:24:08** [pitfalls] **★ `--force-with-lease` is defeated by a background fetch, and the fleet fetches in the background.** Bare `--force-with-lease` "will fail unless you manually run `git fetch origin-push`. This method is of course **entirely defeated by something that runs `git fetch --all`**"; the documented remedy is an explicit expected value (`--force-with-lease=<ref>:<expect>`). `--force-if-includes` adds "the tip of the remote-tracking ref is reachable from one of the **reflog** entries of the local branch" — **another reflog dependence**, and a **no-op** when combined with `--force-with-lease=<refname>:<expect>`. **In-repo refreshers (verified bare):** `skills/commit-workflow/workflow/04-merge-deploy.md:39` (`git fetch origin && git merge origin/main`), `scripts/cleanup-stale-branches.sh:71` (`git fetch origin --prune --quiet`), `scripts/stale-worktrees.sh:53` (`git fetch origin --quiet`). **Non-refresher (corrected):** the pre-PR `git fetch origin "$DEFAULT_BRANCH" --quiet` (`skills/commit-workflow/workflow/01-preflight.md:215`) names an explicit refspec and fetches **only the default branch** ⇒ it does **not** refresh `origin/<feature>`. ⇒ **the push-time base is not a stable identity**, and `--force-with-lease` does not protect against a foreign edit that arrived before the most recent fetch. Source: `man git-push` (Git 2.50.1) + the named in-repo call sites.

- **2026-09-13T12:24:09** [precedent] **(UNSOURCED — do not build on this.)** Forge precedent: GitHub's PR "Files changed" is a three-dot merge-base diff; Gerrit diffs a patch set against its recorded **parent** commit; Phabricator Differential uses the **branch point / merge base** against the target. Directionally: no forge uses "diff against my own remote branch tip." **The GitHub half alone is sourced** — `docs/research/2026-09-11-issue-755-vgate-merge-scope.md:50` cites `docs.github.com → pull-requests/reference/branches`.

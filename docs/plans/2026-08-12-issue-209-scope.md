## Problem Diamond

### Divergence — alternative framings

**Framing 1 — "loadavg is the wrong signal; use cgroup/cpu-time"**
- Strength: loadavg is trailing (1-min average), host-wide, inflated by VM steal,
  blind to cgroup quotas and container neighbors. A quota-capped container can be
  CPU-starved while loadavg reads low; a neighbor's storm can raise loadavg while
  this host is idle.
- Weakness: the fleet is **same-host** — sub-agents are child processes of the pi
  host, batch scripts run on the same host, and the 2026-08-12 storm (load 77–98)
  was host-level and loadavg-visible. Reading cgroup data means new dependencies,
  cgroup v1/v2 path divergence, and still misses host-level contention from other
  workloads — the exact thing that slowed the fleet. `os.loadavg()` ships in Node ≥18,
  zero deps, works on macOS + Linux.
- Assumptions: [validated] fleet workloads are same-host (all sub-agent spawns are
  child processes; batch scripts run on the host); [validated] observed storms are
  host-level (2026-08-12: load 77–98 on 10 cores); [unverified] cgroup quotas are
  in use on fleet hosts (no evidence in repo or docs). Cgroup/VM-steal blindness
  is accepted and **documented as a limitation**, not a blocker.

**Framing 2 — "just raise all bounds statically and rely on retries — no load sensing"**
- Strength: cheapest; the watchdog half structurally needs no load reading. A
  `toolsInFlight > 0` exemption closes the #198 gap in the decision function, a
  static bump (300s → 900s) covers moderate storms, and cut sub-agents are already
  retryable (`resolveUndefined` → re-spawn).
- Weakness: cannot satisfy indicator 2 (batch deferral) at all — deferral exists
  precisely to **stop compounding load**, which no static bound can do. A static
  bump does not scale with storm severity: the 2026-08-12 storm slowed suites 10×,
  so a 15-minute-silent agent at 10× slowdown needs 150 min > any sane static cap.
  And retry-under-load compounds the storm (align doc, adversarial challenge A).
- Assumptions: [validated] watchdog-only fixes the worst symptom cheaply (used as
  the sequencing rationale); [validated] static bounds cannot achieve indicator 2
  or the "defer until load < threshold" target; [validated] retry-under-load is
  harmful (10× slowdown × retry churn).

**Framing 3 — "the real fix is tortoise #1005 (stop the storms); nothing to build here"**
- Strength: root-cause elimination; if the redislite leak is fixed, the specific
  bgsave-storm trigger class disappears.
- Weakness: BGSAVE runs **routinely** (scripts/daily-backup.sh triggers it daily) —
  "assume idle load" is the wrong default regardless of #1005. Other bursts (builds,
  git clones, batches) raise load too. #1005 lives in the tortoise repo (separate
  queue, separate team); defense-in-depth is independent of it and the fleet runs
  continuously.
- Assumptions: [validated] #1005 exists and is tracked in tortoise (research);
  [unverified] its fix lands and eliminates all storm classes. Treat #209 as
  hardening that stands regardless.

**Framing 4 (chosen) — "static watchdog bounds + unconditional batch scheduling collapse under load storms; bounds must scale with load and batches must defer"**
- This is the issue's own framing and it is the one the evidence supports:
  - The first-message clause (index.ts:785–798) never checks `toolsInFlight` (the
    silence clause does, index.ts:774–780) and `parseHeartbeatLine` latches
    `turnSawTool` only from tick `saw_tool` (index.ts:581), not from `tool_start`
    (index.ts:548–550) — so a tool in flight with a lost/pre-tick `saw_tool` is cut
    at 300s instead of the 6h tool-stall bound. **Code-provable today**, and it
    recurred live twice on 2026-08-12 (3/3 wave sub-agents cut; align-run
    exploration sub-agent cut at 738s vs 300s bound).
  - Zero loadavg references anywhere in agent-infra/swarm/tortoise checkouts
    (verified by grep). scripts/daily-backup.sh triggers BGSAVE unconditionally
    (the storm igniter); scripts/cron-quality-gates.sh has no load gate.
  - No shell-out timeout in the tree is env-overridable except the `TASK_*`
    watchdog family (slack-bridge still hardcodes the 2s git cap that flaked in #196).
- Assumptions: [validated] loadavg reflects host contention for same-host fleet
  (Framing 1); [validated] thresholds require hysteresis (single-sample thrash —
  align gap 2); [validated] deferral requires a resume mechanism or it silently
  drops batches (align gap 4 — worse than running under load).

**Framing 5 — "schedule away from storms" (reactive scheduling)**
- Strength: a fixed low-load hour for daily-backup and nice/ionice priority
  lowering are cheap, need no load sensing, and reduce the *probability* of
  overlapping a routine storm trigger (the daily BGSAVE).
- Weakness: reactive, not adaptive — it cannot see storms from builds, git
  bursts, or other batches, and a fixed low-load window does not exist for
  arbitrary storm times; it satisfies none of indicators 1–3 on its own.
- Verdict: rejected as a primary mechanism (F9f); complementary at most — a
  fixed low-load hour for daily-backup and nice/ionice can coexist with the
  load gate, and the policy doc mentions them as optional schedulers-side
  helpers, but they are not part of the #209 contract.

### Convergence — confirmed problem

**Under load storms (bgsave/build/git bursts), static watchdog bounds cut live
sub-agents and unconditional batch scripts compound the load — with no load
sensing, no env-overridable shell-out timeout pattern, and no suspension policy
anywhere in the fleet.** Concretely: (1) a sub-agent with an in-flight tool but a
lost `saw_tool` tick is killed by first-message-stall at 300s while the tool is
still running (the #198 recurrence — E13 never sets `toolsInFlight`, so the gap is
untested); (2) daily-backup.sh triggers the storm-causing BGSAVE unconditionally
and cron-quality-gates.sh runs unconditionally; (3) a 2s git-lookup cap (#196)
flakes under load with no env override.

**Rejected framings:**
- Framing 1 (cgroup/cpu-time): same-host fleet makes loadavg the correct cheap
  signal; cgroup complexity has no demonstrated payoff and still misses host-level
  contention. Limitation documented, not adopted.
- Framing 2 (static bump only): closes the structural gap but cannot defer batches
  (indicator 2) and cannot scale with storm severity (10× slowdown outruns any
  static cap); retry-under-load compounds storms.
- Framing 3 (root cause only): routine BGSAVE + other burst classes make load
  defense necessary regardless of #1005; #1005 is out-of-repo and out of this
  issue's control.
- Framing 5 (schedule away from storms): reactive scheduling is not adaptive —
  it cannot see storms from builds/git bursts/batches and a fixed low-load
  window does not exist for arbitrary storm times; complementary at most (a
  fixed low-load hour for daily-backup plus nice/ionice can coexist with the
  gate), rejected as the primary mechanism because it cannot satisfy indicator 2.

**Falsification test:** the problem is provable in the code as written today —
`heartbeatKillDecision(dinput({ state: st }))` with `st.turnActive = true`,
`st.turnSawMessage = false`, `st.lastMarkerAt` fresh (a recent timestamp),
`st.toolsInFlight = 1`, `st.turnSawTool = false`, `st.streamAgeMs > M` returns
`kill: true` with reason `first-message-stall` (a live tool being cut). This
literal construction matches E13b's state exactly (turnActive=true,
turnSawMessage=false, lastMarkerAt fresh, toolsInFlight=1, turnSawTool=false,
streamAgeMs>M) and is copyable into a test verbatim (F8) — note
`createHeartbeatState` defaults (`turnActive:false`, `lastMarkerAt:0`) would
return kill:false, so the falsification must set them explicitly. If that test returned no-kill today,
there would be no structural gap and the watchdog half of this issue would reduce
to a threshold tweak. Confidence: **high (90/100)** — the failure is code-provable,
recurred live twice on 2026-08-12, and the batch surface is verified unconditional.

## Solution Diamond

### Divergence — solution approaches

**Approach A — full (the issue's ask):**
1. Watchdog: first-message clause gains a `toolsInFlight > 0` exemption (structural
   #198 fix — never cut a live tool; the 6h tool-stall clause remains the bound for
   stuck tools) AND a load-scaled bound: `effM = max(M, round(M × scale(load1)))` —
   load only EXTENDS, never shrinks, never goes below the env-overridable static M.
   Because the bound is recomputed per tick, naive recompute would collapse effM
   back to M the moment a storm ends while `streamAge` is peaked → immediate
   re-cut; effM is therefore latched per dispatch via a **per-run monotonic
   high-water mark** — the bound never shrinks below the run's max for that
   agent (F1). Injectable `load1` field on `HeartbeatDecisionInput` (default 0 =
   no load → scale 1 → legacy behavior).
2. Shared load-gate helper (`scripts/load-gate.mjs`): pure ESM — `readLoad1()`
   (default `os.loadavg()[0]`, injectable), `shouldSuspend`/`shouldResume` with
   threshold + hysteresis, env-overridable, CLI entry for bash wrappers.
3. Batch gating: cron-quality-gates.sh (arch + mutation) and daily-backup.sh gain
   a load-gate preflight — defer with loud log + distinct exit code + resume
   contract (bounded poll, then exit 3; next invocation is the resume;
   `LOAD_GATE_FORCE=1` env escape — no wrapper script flag, scope-pinned F4) **plus a mid-run load re-check** (poll inside the wrapper loop;
   abort-with-exit-3 if load crosses suspend mid-run — matching the watchdog
   half's per-tick freshness; F7). Gating is not entry-only: a batch that passes
   at load 20 aborts if load spikes to 90 mid-run. **The mid-run re-check guards
   the pre-trigger steps ONLY (round-2 F2):** daily-backup's BGSAVE fires BEFORE
   the LASTSAVE poll loop where the re-check lives — once BGSAVE is in flight,
   exit-3's pinned contract ("batch did NOT run; re-invoke") is FALSE, and a
   re-invoke would trigger a SECOND BGSAVE (a storm igniter under load,
   contradicting the anti-compounding principle). After BGSAVE fires, the script
   completes its wait (aborting saves nothing). If an abort-after-trigger is ever
   retained, it must use distinct semantics (e.g. exit 4 / "BGSAVE ran; remaining
   steps deferred") — never the exit-3 "did NOT run; re-invoke" contract. Note
   daily-backup's BGSAVE is itself a storm igniter — the gate defers only under
   *pre-existing* load. Deferral never silently drops a batch.
4. #196 pattern fold: env-overridable shell-out timeout getters — slack-bridge
   `gitRemoteTimeoutMs()` (GIT_REMOTE_TIMEOUT_MS, default 10s) + tree-kill
   `execTimeoutMs()` (TREE_KILL_EXEC_TIMEOUT_MS, default 5s, the kill-path cap) —
   with the #196 branch as provenance. The branch's bounded-retry half (f50b52b)
   is explicitly NOT folded; the folded surface is the getter pattern only (see D2).
- Strengths: satisfies all three indicators + both targets; every piece is pure /
  injectable and unit-testable without a real-load CI generator; defense-in-depth
  that stands regardless of #1005.
- Weaknesses: largest surface; spans three code areas (extension decision fn,
  bash wrappers, shell-out getters) — managed by sequencing (A1→A4 below) and by
  scoping the #196 fold to two liveness-critical caps.

**Approach B — watchdog-only:**
- `toolsInFlight > 0` exemption + static generous bump (M 300s → 900s); no load
  sensing, no batch gating, no helper, no #196 fold.
- Strengths: smallest change, zero new signal sources, closes the #198 structural
  gap (the most damaging symptom — 3/3 sub-agents cut).
- Weaknesses: fails indicators 2 and 3 entirely; static bump doesn't scale with
  storm severity (10× slowdown outruns 900s); storms keep compounding; the #196
  flake class stays un-overridable.

**Approach C — helper-only:**
- Load-gate helper + batch deferral only; no watchdog changes (defer the #198 gap
  to #198).
- Strengths: fixes the load-compounding half; helper reusable cross-repo.
- Weaknesses: leaves the live-sub-agent-cut failure class in place — the most
  damaging symptom — and #198's own fix is stalled; the exemption is a 5-line
  structural fix research already proved.

### Convergence — chosen approach

**Approach A, sequenced A1 → A4.** Each step lands independently and is verifiable:

- **A1 — watchdog structural fix (unconditional, low-risk):** `toolsInFlight > 0`
  exemption in the first-message clause + `load1` field on `HeartbeatDecisionInput`
  (default 0) + `scaleFirstMessageMs()` pure function + `getLoad1()` with test seam
  (default `os.loadavg()[0]`), per-tick load read in the 10s decision loop, effective
  bound shown in the kill headline (per-dispatch high-water-mark latch on the
  effective bound — F1). When effM extends beyond M, emit a `[task]`-prefixed log
  via the existing `console.error('[task] …')` convention (e.g.
  `[task] first-message bound 300s → 900s (load1=60)`) — watchdog-side
  observability (round-2 F1, align gap 5 / research implication 6) so bound
  extensions are verifiable in production without a kill.
  `TASK_FIRST_OUTPUT_TIMEOUT_MS` env override
  added (default 60s unchanged; tier-1 stays NOT load-scaled — scaling tier-1
  delays hung-spawn detection, and spawn retry is cheap and stateless; F9e).
- **A2 — shared helper:** `scripts/load-gate.mjs` + `scripts/load-gate.test.mjs`.
- **A3 — batch gating:** cron-quality-gates.sh + daily-backup.sh preflights.
- **A4 — #196 fold:** slack-bridge git timeout getter + tree-kill exec getter.

**Why not B or C:** B is strictly a subset of A1 (A1's exemption is the same code
plus an injectable field that defaults to legacy); C leaves the worst symptom
(live-agent cuts) unfixed and depends on a stalled issue. A's incremental
structure keeps standard complexity: each step has its own tests and none blocks
the next.

### Decisions resolved

**D1 — Load signal + threshold + hysteresis.**
- Signal: `os.loadavg()[0]` (1-min) via injectable getters on both consumers
  (`getLoad1()` in builtin-tools with a test seam; `readLoad1()` in load-gate.mjs).
  Limitation documented: blind to cgroup quotas / VM steal / container neighbors —
  acceptable for a same-host fleet; env overrides cover per-host tuning.
  macOS (Darwin) semantics (F9b): loadavg counts threads, so per-core readings
  run higher on macOS than Linux; the per-core defaults are calibrated to Linux —
  on macOS, spurious *suspension* is the safe direction (deferrals are loud and
  resumable); the policy doc instructs per-host env thresholds.
- Defaults are **per-core normalized** so a fixed constant means the same thing on
  different hosts, anchored to the wt-291 documented operating point (load ~25–26
  on 10 cores ≈ 2.5×/core):
  - `LOAD_SUSPEND_THRESHOLD` — default `2.5 × os.cpus().length` (10-core host: 25 —
    reproduces wt-291's "< 25" go/no-go point exactly).
  - `LOAD_RESUME_THRESHOLD` — default `1.5 × os.cpus().length` (10-core: 15) — 40%
    hysteresis band; once deferred, a batch waits until load is BELOW resume, so a
    single-sample dip does not thrash.
  - `TASK_LOAD_SCALE_START` — default `1.5 × os.cpus().length` (10-core: 15) —
    first-message bound begins extending at the same level where resume is allowed.
  - `TASK_LOAD_SCALE_MAX` — default 3 — multiplier cap on the first-message bound
    (300s → 900s at load ≥ suspend). Cap rationale: too-generous bounds let hung
    providers linger; the 6h tool-stall clause is the backstop for the in-flight
    case. Under the 2026-08-12 storm (observed load 77–98 on 10 cores), scale saturates at 3 — the observed range is **77–98** (Framing 1 / research); the simulation value (load1 = 60) used in E15/T1/T3 is chosen to saturate (any value ≥ suspend), deliberately distinct from the observed range (round-2 F3).
    **Accepted residual cut class (F5):** at the cap, a first message that
    normally takes >90s is still cut after 900s under a persistent storm (10×
    slowdown ⇒ 900s < 1500s needed). The guarantee is therefore: *no cut for
    first-message latency up to 15 min of storm time; beyond that, capped by
    design* — this is the acceptance wording and is analyzed in the policy doc.
    The alternative (uncapped scale) lets hung providers linger indefinitely,
    which is exactly the failure mode the cap exists to bound.
  - Scale formula (pure): `scale(load1) = 1` when `load1 ≤ start`;
    `min(MAX, 1 + (load1 − start)/(suspend − start) × (MAX − 1))` when
    `start < load1 < suspend`; `MAX` when `load1 ≥ suspend`. Invalid env → defaults.
    **Env-ordering enforcement (round-2 F5):** the mid-band denominator
    (suspend − start) must be > 0 — under misconfiguration (e.g.
    `LOAD_SUSPEND_THRESHOLD=10` with the default start 1.5×cores = 15 on a
    10-core host) it is ≤ 0 and the formula yields NaN/Infinity bounds. Config
    getters therefore clamp: if `suspend ≤ start` or `resume > suspend`, fall
    back to defaults for the offending vars — a NaN/Infinity effM is never
    produced. Same clamp in load-gate.mjs's config getters; one-line note in the
    policy-doc env table.
- Watchdog side reads load **fresh every 10s tick** (os.loadavg is a cheap kernel
  read) so a storm starting mid-run extends the bound; the scale function takes the
  base `firstMessageMs` and never returns below it. The per-tick recompute is
  paired with a **per-dispatch high-water-mark latch** (F1): an agent's effM is
  `max(previous tick's effM, recomputed effM)` — once a storm raises the bound it
  never shrinks below the run's max for that dispatch, so a storm ending while
  `streamAge` is peaked cannot trigger an immediate re-cut.

**D2 — Supersede semantics (#198/#196).**
- #198: the `toolsInFlight > 0` exemption + load-scaled bound **replaces** #198's
  static-bump approach — but is **layered on top of** the existing env-overridable
  `TASK_FIRST_MESSAGE_MS`: `effM = max(getFirstMessageMs(), round(getFirstMessageMs()
  × scale(load1)))`. Never below the static value, all existing envs/clamps
  unchanged, and at `load1 = 0` the load-scaling path is inert (scale = 1, so
  effM = M exactly) — the `toolsInFlight > 0` exemption is a **DELIBERATE
  behavior change** (not a load-path side effect) pinned by E13b; the default-0
  `load1` field keeps all 1000+ existing assertions green (round-2 F4). If
  #198 is still open, it is
  closed as superseded when A1 lands; if merged, A1 layers on it. The exemption is
  safe by construction: the tool-stall clause (precedence #1) still bounds stuck
  tools at L=6h, and the opt-in max-dispatch cap remains the pathological-loop
  backstop.
- #196: **fold the pattern into #209; do not land the branch first.**
  Justification: (a) `origin/fix/slack-bridge-git-timeout-196` has sat unmerged
  through review (#205) — landing it now adds a merge of a duplicated-code branch
  to main before #209 starts; (b) research proved the hardcoded-cap class is
  pervasive (15+ git/exec shell-out caps, zero env overrides), so a one-instance
  branch land fixes one flake while the pattern needs a uniform home anyway;
  (c) #209 indicator 3 is exactly "env-overridable shell-out timeouts" — folding
  lands the pattern once, with tests, and the branch's commits serve as provenance
  for the getter shape. Scope guard: fold only the two liveness-critical caps —
  slack-bridge `GIT_REMOTE_TIMEOUT_MS` (the #196 content: 2s → 10s default, env
  override, invalid → default) and tree-kill `EXEC_TIMEOUT_MS` (2s → 5s default;
  the kill-path cap — a watchdog that fires but cannot kill leaves a zombie).
  The remaining 14 hardcoded caps (incl. slack-bridge `GH_API_TIMEOUT_MS`,
  L964/1101, 15s — F9d) are documented as a follow-up surface (below),
  not #209 work.
  **#196 bounded-retry half — explicitly out of scope (F6):** the reviewed branch
  (f50b52b) pairs the 5s cap with "one bounded retry in BOTH duplicated copies";
  this fold drops the retry half, superseded by the getter pattern alone.
  Rationale: (a) an env-overridable generous default (10s) with invalid→default
  handles the flake class deterministically at the timeout source — no second
  code path per call site; (b) retry-under-load compounds storms
  (anti-compounding principle, Framing 2 weakness) — a retry during a
  bgsave/git burst is the exact compounding this issue targets; (c) the kill-path
  cap must not retry (a watchdog that waits on a retry cannot kill). The folded
  surface is therefore a justified subset of the reviewed branch; a retry, if
  ever needed, is a follow-up.
  **Indicator-3 wording pin (F9c):** #209 delivers indicator 3 as
  *"env-overridable with sane static defaults (10s/5s); load-awareness lives in
  the watchdog bound"* — explicitly NOT load-aware shell-out timeouts. Deliberate
  wording drift from any load-aware reading: shell-out caps are tail-latency
  controls, not storm controls (storms compound through retries and spawns,
  which the watchdog and gating halves handle); pinned so the objective cannot
  be read as silently broadening the fold.

**D3 — Helper home + resume mechanism.**
- Home: `scripts/load-gate.mjs` (pure ESM, zero deps, `node`-runnable — bash
  wrappers consume it via CLI: `node scripts/load-gate.mjs check [--deferred]
  [--json] [--force]`, exit 0 = go / 2 = usage-error / 3 = defer). The watchdog's
  scale lives in builtin-tools (same file family as the `TASK_*` getters) with its
  own `TASK_LOAD_*` envs — deliberately NOT imported across tree boundaries
  (extensions load via pi's TS loader; scripts run under plain node; a shared
  import would couple the two runtimes). Parity = the one `os.loadavg()[0]` default
  line, covered by tests on both sides and pinned in the policy doc.
- wt-291 provenance: the original gated-rerun script is **not locatable** in any
  checkout (tortoise main + worktrees, swarm — verified by grep in research). The
  helper is therefore a **fresh extraction specification** informed by the
  documented operating point (2026-08-07 p1-bugs-batch1 run note: "loadavg ~26",
  wait "load < 25" on 10 cores) — our per-core defaults reproduce it exactly.
- Resume mechanism (defer never silently drops): (1) **entry gate** — `check`
  exits 3 when `load1 ≥ suspend`; (2) **bounded poll** — the wrapper re-checks with
  `check --deferred` every 60s up to `LOAD_GATE_MAX_WAIT_MIN` (default 10); (3)
  **exit-3 contract** — after the cap, the wrapper exits 3 with a loud
  `[load-gate] DEFERRED — batch did NOT run; re-invoke after load < N (was M)` line;
  exit 3 is distinct from 0/1/2 so invokers cannot mistake it for success, and the
  script headers document that the invoker MUST re-invoke (skills re-dispatch;
  daily-backup resumes at its next daily invocation — **RPO ≤ 48h, not 24h (F2)**:
  a deferral near one daily invocation can slip to the next, so under sustained
  load the gap is up to 48h+ — accepted trade for load safety; `LOAD_GATE_FORCE=1`
  is the documented emergency escape (env-pinned; both wrappers accept the env
  directly, no script flag — the helper CLI's `--force` shorthand merely sets it)). (4) **mid-run
  re-check (F7)** — the wrapper polls `check` inside its run loop and aborts with
  exit 3 (loud defer log) if `load1` crosses suspend mid-run; gating is not
  entry-only, matching the watchdog half's per-tick freshness. **The mid-run
  re-check guards the pre-trigger steps ONLY (round-2 F2):** daily-backup's BGSAVE
  fires BEFORE the LASTSAVE poll loop where the re-check lives — once BGSAVE is in
  flight, exit-3's pinned contract ("batch did NOT run; re-invoke") is FALSE, and a
  re-invoke would trigger a SECOND BGSAVE (a storm igniter under load,
  contradicting the anti-compounding principle). After BGSAVE fires, the script
  completes its wait (aborting saves nothing). If an abort-after-trigger is ever
  retained, it must use distinct semantics (e.g. exit 4 / "BGSAVE ran; remaining
  steps deferred") — never the exit-3 "did NOT run; re-invoke" contract. When the
  pre-trigger re-check does abort, the defer log must say
  `[load-gate] DEFERRED — partial: BGSAVE may have run; re-invoke to complete
  copy` where applicable — the abort guards the pre-trigger steps, not an
  already-triggered save (round-2 F6). Note daily-backup's
  BGSAVE is itself a storm igniter — the gate defers only under *pre-existing*
  load. A deferral is a promise to re-run, not a skip.
- **Daily-backup invoker is unidentified in-repo (F2):** no crontab/schedule
  entry for daily-backup.sh exists in any checkout, so the exit-3 re-invoke
  contract depends on an external invoker whose exit-code handling is unknown.
  If the invoker cannot re-invoke (no cron entry reacts to exit 3), the
  daily-backup contract degrades to **loud failure requiring human re-invoke**
  (the defer log + exit 3 at minimum surface the miss); documented in the policy
  doc. Wiring the invoker itself is out of scope.
- Cross-repo consumption (swarm): the CLI contract (exit codes, envs, `--json`
  output) is the documented surface for swarm's Python scheduler
  (`operations/coordination/state_machine.py`) to consume the same semantics later
  via subprocess — a code change there is explicitly out of scope, the contract is
  the deliverable.

**D4 — Tests.**
- E13 update: existing E13 assertions stay (toolsInFlight=0 → still cut); new E13b:
  identical state + `st.toolsInFlight = 1` → `{ kill: false }` (the gap case, red
  today).
- E15 (new): load scaling — `dinput({ load1: 60, ... })` with streamAge = M+1 →
  no kill; streamAge > 3×M → kill (capped); `load1` between start and suspend →
  proportional bound; `load1: 0` → legacy (bound = M exactly). The mid-band
  `load1` is computed from `os.cpus().length` (e.g. `2.0 × cores`) or explicit
  thresholds are passed in the dinput, so the proportional assertion is not
  core-count dependent (F9a).
- E15b (new, F1): multi-tick high-water-mark — ticks with `load1 = 60` while
  streamAge grows past M (bound extends), then a tick with `load1 = 2` (naive
  recompute would collapse effM to M) → **no kill**: the per-dispatch latch
  keeps effM at the run's max.
- E16 (new, F4): loop-level wiring — stub `getLoad1()` via the test seam, run
  the 10s decision loop across ticks, assert `HeartbeatDecisionInput.firstMessageMs`
  actually varies with load, and that a tick after load drops passes the latched

## External validation (Perplexity research, 2026-08-12)

Load-average semantics research adds nuance (no design change):
- loadavg includes tasks waiting on I/O, not just CPU contention (Netdata
  "Linux Load Average Myths and Realities") — this makes loadavg SENSITIVE to
  exactly the BGSAVE-storm class this issue targets (I/O-heavy), confirming
  it as the right signal.
- The 1-min average is an exponentially decaying average, not a pure 60s
  window (Wikipedia, Load (computing)) — supports keeping hysteresis rather
  than trusting a single sample (already in scope).
- Some systems count threads as processes; macOS idle systems can show load
  > 1.0; multi-threaded workloads can double-count and create artificial
  spikes (Netdata; Ask Different) — reinforces the existing macOS-semantics
  note and per-host env thresholds, and that suspension (defer, never kill)
  is the safe failure direction.

## Stage 3 — Scope (double diamond, standard depth)

### 1. PROBLEM-DIVERGE — alternative framings

**Framing A — "The 6h block is a bound-tuning problem: lower the tool-stall
bound."** The observed ~6h delay is exactly `DEFAULT_TOOL_STALL_MS =
21_600_000` (builtin-tools L436), so shrink it (6h → 30min).

- Strength: smallest change; the number in the incident is literally the bound.
- Weakness: (a) reintroduces the #489 class — real tools (deploys, batch
  reads) legitimately exceed 30 min; the 6h ceiling is deliberate (align
  condition 3). (b) It fixes nothing about the *mechanism*: every existing
  bound resolves through kill-then-`close` (research §2b), and `close` is
  delayed indefinitely by a surviving pipe-holder — so even a 30min bound
  becomes a 30min *minimum* block, and an orphan that holds the pipes until
  its own death can still exceed any lowered bound. (c) Leaves the cut-reason
  collapse (subagent ext resolves external kills as `exitCode 0`) and the
  orphan surface untouched. Fails indicators 1–3 as written.
- Assumptions: [validated] 6h = `DEFAULT_TOOL_STALL_MS` (research §2a);
  [validated] all bounds are defeated by pipe-holding orphans (research
  §2b/§4, no `exit` handler anywhere — grep: `close`/`error` only in both
  tools); [validated] long tools exist → #489 class (align A).

**Framing B — "The problem is the watchdog killing live work: fix #198's
false kills, nothing else."** If cuts never happen, no 6h block, no orphans.

- Strength: addresses the triggering event class of #198.
- Weakness: the observed incident was an *external* cut (harness/provider),
  not an internal false kill (research §1; the surviving 0%-CPU PID 6632 fork
  is re-attributed as the pipe-holding orphan GRANDCHILD — evidence for the
  sweep surface, not for a wedged-alive child class, §2 account X); per-task timeout
  and abort kills are internal but still flow through the same close-only
  resolve; even perfect kill decisions leave the parent blocked 6h on a dead
  child and orphans holding worktrees/MCP pairs. Fails indicators 1–2.
- Assumptions: [unverified] cuts are mostly internal false positives —
  research observed the opposite; [validated] timeout/abort/external kills
  all share the close-only resolve defect (research §1/§2b).

**Framing C — "Orphans are the real issue: sweep-only fix."**

- Strength: directly serves indicator 2; `treeKill` + a sweep is precedent-
  backed (#137/#153).
- Weakness: without a settle fix the sweep cannot even run usefully — the
  parent's `await` is still unbounded (orphan holds pipes → `close` never
  fires → `doResolve` never runs), so the orchestrator blocks 6h regardless
  of any sweep. A pgid sweep on today's non-detached builtin spawn would hit
  the parent's own group (research §3); a name/pid sweep risks the
  orchestrator's own session and PID recycling. No cut reason → no resume
  (indicator 3 unmet). Fails indicators 1 and 3.
- Assumptions: [validated] orphan-holding-pipes is the 6h mechanism
  (research §2b); [validated] `treeKill`'s PPID walk breaks on reparented
  orphans — PPID→1 (research §3, tree-kill.ts L28–48); [validated] builtin
  spawn is non-detached → shares parent pgid (research §3).

**Framing D — "Child-side self-terminate: the child detects its own provider
disconnect and exits cleanly, closing the pipes."** No parent-side wait or
sweep needed — the child is the first to know.

- Strength: closes the pipes at the source; no sweep, no kill-path change.
- Weakness: does not cover the wedged class (a wedged child cannot act on
  anything); provider-side cuts are often invisible to the child (the parent
  observes a dead request stream while the child still believes it is
  connected — consistent with account X, §2, where the child died externally
  without self-terminating); still needs the exit/close resolvers for the
  cases where the child DOES die. Fails indicators 1–2 as a standalone.
- Assumptions: [unverified] the child can reliably detect the cut — the
  observed incident contradicts this (the child died externally, leaving an
  orphan holding the pipes; no self-termination occurred).

### 2. PROBLEM-CONVERGE — confirmed problem

**Confirmed problem: parent-side dispatch has no bounded wait, no cut
contract, and no identity-anchored orphan sweep when a child dies
externally.**

Mechanism (fully traced, research §1–§4, line-verified):

1. Both tools resolve only on `proc.on("close")`; neither has an `exit`
   handler (grep: `close`/`error` only — subagent L537/L562, builtin
   L1274/L1297). A grandchild (MCP server / bash fork) holding the inherited
   pipes delays `close` indefinitely → the parent's await survives the
   child's death → unbounded block.

2. Two candidate accounts explain the observed ~6h:
   **(X) child dead early, orphan holds pipes** — the child was cut
   externally ~300s in; a forked pipe-holding grandchild delayed `close`
   until the orphan itself died ~6h later. `close` is the only resolver, so
   the parent's await survived the child's death by the orphan's lifetime.
   **(Y) child alive-but-wedged** — no markers, 0% CPU; tool-stall at 6h
   (heartbeatKillDecision L759–766; first-message requires `!turnSawTool`
   L792–798). **Y is ruled out for the observed incident**: tool-stall
   requires `stateFresh`, i.e. markerAge ≤ max(2×T, 2×interval) = 60 min
   with defaults (L748–750) — a marker stream frozen > 60 min can NEVER trip
   tool-stall. And the observed 0%-CPU PID 6632 is re-attributed as the
   orphan GRANDCHILD (a pipe-holder's 0% CPU is evidence for the SWEEP
   surface, not for a wedged-not-ticking child, which remains
   hypothesized/unobserved). **X is the observed account**; the marker-gap
   cut clause (D1) is defense-in-depth for the hypothesized wedged class.

3. The subagent ext collapses an external signal-kill to `resolve(code ?? 0)`
   with no `stopReason` (L562) → `isFailedResult` returns false (L190–196) →
   a cut is indistinguishable from SUCCESS.
4. The builtin heartbeat kill is a single-pid `proc.kill("SIGTERM")` (L1241)
   with a non-detached spawn (shares the parent's pgid) — children-of-the-
   child survive the cut, hold the pipes, and a pgid sweep is currently
   unsafe by construction.
5. No wall-clock backstop on either parent await (`TASK_MAX_DISPATCH_MS`
   opt-in, default 0, L469–472); the exit watchdog (120s) only reaps a
   specific hang-alive-at-spawn class.

**Falsification test:** construct the negative case today — dispatch via
builtin task tool, have the child fork a pipe-holding grandchild and exit
mid-tool. Expected today: parent does not resolve (blocks ≥ 6h). The same-day
incident (2026-08-12 wave, ~6h blocks) is the observed falsification of the
"no problem" hypothesis. After the fix, the same construction must resolve
< 60s with partials + a cut reason (this construction becomes the headline
integration test).

**Rejected framings:** A (bound tuning — #489 regression + mechanism
untouched), B (kill-decision-only — external cuts remain, block mechanism
untouched), C (sweep-only — unbounded wait and cut-reason gap remain),
D (child-side self-terminate — does not cover the wedged class, and
provider-side cuts are often invisible to the child).

**Confidence: 85/100** — mechanism line-traced in both tools; incident
observed same-day; account X (orphan lifetime ≈ 6h, §2) fits the stateFresh
analysis (a >60-min-frozen marker stream cannot trip tool-stall) and the
0%-CPU PID 6632 re-attribution; account Y (wedged-alive child) remains
hypothesized/unobserved and is not needed to explain the incident.

### 3. SOLUTION-DIVERGE — approaches

**Approach A — Full dispatch contract (both tools): exit-event settle +
marker-gap cut clause + cut reason + identity-anchored sweep + doc
guidance.**

1. Add a `proc.on("exit")` resolver in BOTH tools as a **grace-race, not
   settle-on-exit**: Node's `exit` fires BEFORE `close`, and the final-output
   composition lives in the close path (builtin `flushHeartbeatLineBuf` #176
   + the #134 clean-exit stdout/stderr split L1274–1295; ext `processLine` +
   timedOut/wasAborted stopReason mapping L537–561). Spec: on `exit`, defer
   settle by a short grace (2s); if `close` fires within the grace the NORMAL
   path is unchanged; only when `close` has NOT fired within grace
   (orphan-holds-pipes) does the exit settle run, replicating the finalize
   composition (flush + stopReason branches) with the accumulated partials —
   the pipeline already buffers incrementally. **Settle-exactly-once (F1):**
   a per-dispatch `settled` flag gates EVERY settle path — exit-settle,
   close, backstop — so the settle + its sweep hook run EXACTLY ONCE; the 2s
   grace timer is CLEARED when `close` fires first (a stale timer can never
   fire later and signal a recycled pgid). **resolveUndefined (F10):** the
   exit-settle cut path resolves with `resolveUndefined = !hasOutput` —
   zero-partial cuts stay retryable by the retry wrapper, mirroring the
   kill-clause contract (D6).
   Regression guard: a happy-path tail-completeness assertion (final stdout
   bytes present, stderr→details intact) in the integration suite.
2. Builtin tool: new `"cut"` clause in `heartbeatKillDecision` — marker-gap
   deadline (see decision D1). Reuses the existing kill-result composition
   (`killed: true, reason`, headline "Partial results below — parent should
   decide: accept, re-dispatch, or escalate.", L1259–1272) and
   `resolveUndefined=false` when partials exist.
3. Cut reason in the subagent ext: external signal-kill (`close` code null,
   neither timedOut nor wasAborted) → `stopReason: "cut"`; extend
   `isFailedResult` and surface partials in `getResultOutput` (mirrors the
   #137 timeout treatment). F6 result cache already persists every dispatch
   (L401–403, L585) → cut results are recoverable. Documented limitation:
   the ext has no tool state, so a CLEAN mid-tool exit is undetectable there
   — only signal-death maps to cut (taxonomy in D6). The mapping lives in
   the finalize composition shared by the close path and the exit-settle
   fallback (the grace race must not lose the stopReason branches).
4. Sweep: switch builtin spawn to `detached` (opt-out env, parity with
   `SUBAGENT_DETACHED=0`, #137 F8), capture the child pgid at spawn, and run
   a shared pgid-anchored sweep on the SETTLE PATH (round-3 F2): whenever the
   exit-settle path resolved (close didn't fire within grace — a live
   pipe-holder keeps the pgid alive, so pgid-recycle risk does not apply
   there, regardless of exit reason, incl. clean code-0 with toolsInFlight=0),
   PLUS abnormal reasons (internal kill, cut, signal-death, non-zero exit,
   backstop) resolved via the normal close path; no-sweep for close-within-
   grace only (with a normal result); pgid-recycle safety, D2), with a runtime
   guard for the opt-out config (skip + warn when the
   target pgid equals the parent's own pgid or the spawn was non-detached).
   Shared helper (see D2).
5. Switch the builtin heartbeat kill from single-pid `proc.kill` to
   `treeKill` (precedent: subagent ext L473, exit watchdog L306) so internal
   kills close the pipes promptly; the sweep catches reparented survivors.
6. Backstop timer on each parent await, **gated on detector-dead state** —
   builtin: fires only when `stateFresh === false` (marker stream stale
   beyond the fresh window), healthy ticking agents exempt by construction;
   ext (round-3 F1, option a): **byte-freshness proxy** — fires only when no
   stdout/stderr bytes within the fresh window (60 min), weaker semantics
   documented: a >60-min-silent healthy ext agent is NOT exempt (D4).
7. Doc: new "Cut / Assume-Dead Handling" subsection + Anti-Patterns row in
   parallel-orchestrator (see D5).

- Tradeoffs: largest surface (both extensions + shared helper + tests +
  doc); every piece is small and precedent-backed; resolve-semantics change
  is the one regression risk (mitigated by once-guards + full existing suite
  as net).
- Risks: marker-gap calibration firing on busy-but-ticking agents
  (mitigated: markers reset `lastMarkerAt` on every receipt, L543 — a ticking
  agent is exempt by construction; calibration D1); sweep hitting live
  processes (mitigated: detached pgid exclusion envelope is by construction,
  D2); re-dispatch clobbering partial writes (mitigated: commit-early +
  idempotency guidance + F6 cache, D5).

**Approach B — Detached spawn + process-group kill everywhere (parity with
the subagent ext), plus resolver fix; sweep by pgid only.**

Same as A minus the marker-gap clause: rely on `exit` settle for dead-child
cuts and the existing clauses for the wedged class (tool-stall at 6h for
flowing markers; ~60min via silence at stateFresh expiry for frozen markers
— F7).

- Tradeoffs: simpler (no new kill clause, no calibration risk); covers the
  OBSERVED class (process death → exit-settle), but the hypothesized
  wedged-alive class (markers stopped, process alive — never directly
  observed; PID 6632 re-attributed as the orphan grandchild, §2) would still
  resolve only at ~60min (silence at stateFresh expiry — tool-stall can
  NEVER fire once the marker stream is stale beyond the 60min fresh window,
  F7) — the 60s target is unreachable for that class without liveness
  detection (align condition 1).
- Risks: same as A minus calibration; accepts the ~60min latency for
  frozen-marker wedged cuts (silence at stateFresh expiry) and the 6h
  tool-stall latency for flowing-marker wedges (F7).

**Approach C — Sweep-only + doc (minimal).**

- Tradeoffs: smallest change; does not meet indicators 1 or 3 (unbounded
  parent wait and cut-reason collapse remain); sweep anchoring still forces
  the detached decision without any of its benefits. Rejected.

### 4. SOLUTION-CONVERGE — chosen approach + decisions

**Chosen: Approach A (full contract).** It is the only approach that meets
all three indicators; B is A minus the marker-gap clause (defense-in-depth
for the hypothesized wedged class — without it that class still waits for
~60min, silence at stateFresh expiry — F7), and C meets none of the
parent-side indicators. All four align conditions resolve cleanly inside A.

#### Decision D1 — Operational cut definition (align condition 1)

A cut is **process death, detected by `exit`** (the observed class, account
X, §2) **or liveness loss, detected by marker gap** (the hypothesized
wedged-alive class — defense-in-depth, kept because it is cheap and
unit-testable, but NOT the observed mode) — two detectors, two classes:

| Cut class | Detector | Latency |
|---|---|---|
| Child dies (external SIGKILL/exit) — observed class | grace-race `exit`-settle in both tools (settle deferred 2s; `close` within grace → normal path) | ≤ ~2s (sub-second when `close` beats the grace) |
| Child alive but wedged (markers stopped — hypothesized class; PID 6632 re-attributed as orphan grandchild, §2) | new `"cut"` clause in `heartbeatKillDecision`: `stateFresh && toolsInFlight > 0 && markerAge > cutGapMs` | `cutGapMs` + ≤ 1 tick (10s, L1272) + ≤5s SIGKILL escalation + 2s grace ≈ ~54.5s worst (F3) |

**Calibration (F8 decision, revised by round-2 F3): `cutGapMs = 1.25 ×
HEARTBEAT_INTERVAL_MS`** (default 1.25 × 30s = 37.5s), floor 15s (fast test
bounds: interval floor is 5s, L432). Rationale: (a) the `markerAge`/
`lastMarkerAt` plumbing already exists
(L490, L503, L543) — every marker receipt resets it, so a busy-but-ticking
agent is exempt *by construction* (#176 semantics: the child's emitter ticks
regardless of tool activity; the silence exemption already treats marker-
streaming as alive, L774–778); (b) **Kill-path latency forces the
calibration (F3):** 1.5× interval (45s) + one 10s decision tick = 55s BEFORE
kill latency — and for the wedged (SIGSTOP) class the SIGTERM is queued
while stopped, so the 5s SIGKILL escalation + 2s exit-settle grace push
worst-case resolve to ~62s, marginal vs the 60s indicator. **So the cut gap
is 1.25× interval (37.5s): worst case 37.5s + 1 tick + ≤5s kill + 2s grace ≈
54.5s ≤ 60s with margin**; the sweep runs fire-and-forget AFTER resolve, so
sweep latency (~5s) does NOT count against the resolve indicator (F3). A
default-config bound assertion (1.25× interval + 1 tick + kill path + grace
≤ 60s) lands in the E-series. Jitter/loss bound (F6): the threshold absorbs
~ONE INTERVAL OF JITTER only when the next marker arrives before the firing
point (cutGap + 1 tick ≈ 47.5s); a genuinely lost single marker can fire the
cut at ≤ 47.5s — the bound is explicit, replacing the earlier "absorbs one
dropped marker" claim; (c) the existing "effective ages include time since
last marker" fix (L747–753) already makes `effToolAge` grow past tool-stall
when ticks stop — but with markers stopped `stateFresh` expires at 60min and
tool-stall can never fire: the frozen-marker class would otherwise resolve
at ~60min via silence at stateFresh expiry, so the cut clause shortens that
wait from ~60min to ~37.5s (47.5s incl. tick) — F7. Flowing-marker wedges
(markers tick, a single tool's `effToolAge` > tool-stall) remain at
tool-stall 6h — OUTSIDE the cut clause's reach (markerAge < cutGap by
construction) — F7. Precedence placement: between silence and
first-message (tool-stall → stream-stall → silence → **cut** → first-message
→ max-dispatch); the clause is a liveness detector, orthogonal to tool-stall
(age of a *live* tool) — a 5h deploy with ticking markers never fires it.
`stateFresh` is inherited from tool-stall: cut fires ONLY while stateFresh
(markerAge ≤ max(2×T, 2×interval) = 60 min), so a marker stream stale beyond
the fresh window can never trip cut (the backstop owns that window, D4) —
this interaction is pinned explicitly in the E10 precedence test (F9a). This
does NOT fire on marker-gap with `toolsInFlight == 0` (that class is silence
at T=30min, unchanged). **Do not lower `DEFAULT_TOOL_STALL_MS`** (align
condition 3). Unit-testable as a pure decision (extend the E-series; E10
pins precedence).

#### Decision D2 — Sweep anchor (align condition 2): pgid, after switching the builtin spawn to detached

- **Switch the builtin task spawn to `detached: true`** with an opt-out
  env (`TASK_DETACHED=0`), parity with the subagent ext (`SUBAGENT_DETACHED`,
  #137 F8). Default-detached: the child gets its own pgid; the parent's pgid
  can never equal it → **exclusion envelope by construction** (asserted in
  tests). **F2 — the opt-out re-opens the hazard:** with
  `TASK_DETACHED=0`/`SUBAGENT_DETACHED=0` the child shares the parent's pgid
  and a settle-path sweep would TERM/KILL the orchestrator's own group. The
  shared sweep helper therefore carries a RUNTIME GUARD: skip + warn when
  the target pgid equals the parent's own pgid
  (`process.getpgid(process.pid)`) or when the spawn was non-detached; a
  test for the opt-out config asserts the parent's group is never signaled.
  (Optional hardening: `*_DETACHED=0` implies `*_SWEEP=0`.)
- **Sweep anchored on the captured pgid**, not ppid-walk (`treeKill` breaks
  on reparented orphans, PPID→1) and not argv matching (`pgrep -f` nonce
  matches forks but misses MCP servers whose argv differs — the nonce is
  env-carried, L1130, and pgrep matches argv only). **pgid persists across
  reparenting** and covers forks AND MCP servers in one group.
- **F5 — sweep gating is SETTLE-PATH-based (round-3 F2), not reason-based:**
  the sweep runs (a) whenever the **exit-settle** path resolved — `close` did
  NOT fire within the 2s grace, which by construction means a live
  pipe-holder keeps the child's pgid alive → pgid-recycle risk does NOT
  apply there, so the sweep runs REGARDLESS of the exit reason (including a
  CLEAN code-0 exit with `toolsInFlight == 0` — the deterministic orphan
  class where a forked bg-job/MCP-server holds the pipes and the parent
  would otherwise resolve success and leak the orphan: the same orphan
  mechanism as the incident minus the cut); and (b) on **abnormal reasons
  resolved via the normal close path** (internal kill, cut, signal-death,
  non-zero exit, backstop). **No-sweep ONLY for close-within-grace with a
  normal result** — close firing within grace means the pipes closed (no
  live pipe-holder) and the pgid may be dead/recyclable, so a sweep there
  could TERM/KILL an unrelated group that reused the id; identity
  verification (known member pid / leader start time) stays an option if
  the race proves real. Sweep sequence via the shared helper: `pgrep -g
  <pgid>` → SIGTERM → 5s → SIGKILL → verify empty. Safety valve env
  `TASK_SWEEP=0` / `SUBAGENT_SWEEP=0` to disable.
- **Verify-empty failure semantics (F9d):** if survivors remain after
  SIGKILL, the helper logs a warning and resolves WITH warning (never blocks
  the settle). Residual: a setsid-escaped process leaves the group — the
  `pgrep -f <marker-nonce>` argv pattern is the COMPLEMENTARY catch
  (residual: argv-differing MCP servers are not matched).
- **Settle-exactly-once gate (F1):** the sweep hook is gated by the same
  per-dispatch `settled` flag as the settle — settle + sweep run EXACTLY
  ONCE per dispatch; the grace timer is cleared when `close` fires, closing
  the deterministic recycled-pgid re-fire window (a stale timer or a second
  settle could otherwise signal a pgid already reused by a later dispatch).
  **The sweep runs fire-and-forget AFTER resolve (F3)** — it never blocks
  the settle, so sweep latency (~5s) does not count against the resolve
  indicator.
- The `pgrep -f <marker>` pattern stays as the *test* assertion
  (timeout-integration L110–120 precedent), not the production sweep.
- **F9c — detached semantics note:** detached spawn changes
  terminal-signal/job-control semantics — Ctrl+C / terminal SIGINT no longer
  propagates to the child and job control (fg/bg) no longer applies; the
  sweep is the cleanup path for interrupted dispatches.
- **#195 coordination:** a killed mid-write orphan can leave
  `index.lock`/partial worktree state — the sweep helper's kill log line and
  the skill doc both direct to the existing worktree-recovery path when a
  killed pid's cwd is a worktree (doc-level coupling, no code dependency).

#### Decision D3 — Shared helper boundary

**Share the sweep, not the resolver.** New `extensions/shared/process-sweep.ts`
exporting `sweepProcessGroup(pgid, {signal, timeoutMs})` (and a
`killProcessGroup(pgid, signal)` primitive — the `process.kill(-pgid)` /
`pgrep -g` pattern, extending the tree-kill precedent file's domain). Both
tools call it on the settle-path basis (D2/F5): whenever the exit-settle
path resolved (close didn't fire within grace — a live pipe-holder keeps the
pgid alive), or abnormal reasons (kill/cut/signal-death/non-zero/backstop)
resolved via the close path; no-sweep only for close-within-grace with a
normal result. The *resolvers* stay per-tool: result
shapes differ (builtin `details {killed, reason}` vs ext `SingleResult
{stopReason}`) and each exit-settle is ~5 lines; a shared resolver would
couple the two result contracts for no gain. The pure cut-reason mapping is a
per-tool branch implemented in the FINALIZE composition shared by the close
path and the exit-settle fallback (the grace race must not lose the
stopReason branches); taxonomy in D6, unit-tested in each tool's suite.

#### Decision D4 — Parent bounded-wait value (the "600s?" question)

**Layered, not a single fixed value.** A flat 600s wall-clock cap would kill
legitimately long tools (the #489 class again — a 5h deploy with ticking
markers must not be cut). The parent's await is bounded by three layers:

1. `exit`-settle — grace-race settle ≤ ~2s after child death (primary fix).
2. `"cut"` clause — resolves the frozen-marker wedged-alive class at
   `cutGapMs` (~37.5s; ~47.5s incl. decision tick).
3. **Backstop timer** on the parent await = *longest legitimate bound +
   settle margin*: builtin tool → `DEFAULT_TOOL_STALL_MS + 30min`
   (6h30m = 23_400_000 ms). Subagent ext → `taskTimeoutMs + 15min` when
   taskTimeout > 0; a FIXED `DEFAULT_TOOL_STALL_MS + 30min` (6h30m) when
   `SUBAGENT_TASK_TIMEOUT_MS=0` — the timeout opt-out must NOT reinstate the
   unbounded wait, because the ext has no marker clause to bound a
   long-lived child otherwise. **The ext's firing gate is a byte-freshness
   proxy (round-3 F1, option a) — see the firing-gate paragraph: the ext has
   NO `stateFresh` (no marker stream), so the builtin's marker gate does not
   exist there.** An explicit env opt-out of the backstop
   itself is retained for deliberate unbounded-wait configurations.

**Firing gate (F2): the backstop is NOT a plain wall-clock dispatch cap.** A
timer that fired purely on elapsed time would be a de-facto default-ON total
dispatch cap that cuts a HEALTHY >6h30m multi-tool agent (markers ticking,
no single tool > 6h → tool-stall never fires) — contradicting the
"never kill a working agent" semantics behind `TASK_MAX_DISPATCH_MS` being
opt-in.

- **Builtin tool (has a marker stream):** fires ONLY when
  **`stateFresh === false`** at the moment the timer elapses — marker stream
  stale beyond the fresh window (markerAge > max(2×T, 2×interval) = 60min)
  with no clause able to fire — matching its stated rationale as the
  last-resort for the detector-dead window. A healthy ticking agent
  (stateFresh true) is exempt BY CONSTRUCTION.
- **Subagent ext (NO marker stream — round-3 F1 DECISION, option a):
  byte-freshness proxy.** `stateFresh` is vacuous for the ext (no marker
  emitter by design — Out-of-scope), so the gate is derived from OUTPUT
  ACTIVITY instead: the backstop fires only when the dispatch has emitted no
  stdout/stderr bytes within the fresh window (60 min), sampled from the
  existing incremental pipe accumulator (no new instrumentation). **Weaker
  semantics, documented explicitly: unlike the builtin's marker gate, a
  >60-min-silent healthy ext agent is NOT exempt** — a healthy ext worker
  that legitimately produces no output for >60 min can be cut by the
  backstop (the ext emits no liveness signal; the timeout=0 config accepts
  this as the price of bounding an otherwise-unbounded wait).

The env opt-out stays for deliberate unbounded-wait configurations.

**Result contract on backstop resolve (F5):** builtin composes
`details {killed: true, reason: "cut"}` with max-dispatch-style semantics —
`resolveUndefined = false` when partials exist (same contract as the
marker-gap kill clause); ext sets `stopReason: "cut"` (exitCode stays 0).
The backstop IS an abnormal settle path → the pgid sweep hook runs (D2),
gated by the same per-dispatch `settled` flag as the settle (F1) so the
sweep still fires exactly once.

Wording reconciliation (F9b + F2): the practical post-fix ceiling is

## External validation (Perplexity research, 2026-08-12)

Process-group supervision research confirms the sweep design:
- Standard supervisor best practice: start the workload in its own process
  group/session (detached spawn), send termination to the WHOLE PGID
  (`kill -- -PGID`), wait for exit, then reap remaining children.
- PPID-walk cleanup is documented as insufficient/racy — it misses
  grandchildren, processes that fork at the wrong moment, and children
  already reparented to init — which is exactly why `treeKill`'s PPID walk
  breaks on reparented orphans and the pgid anchor (after detached spawn) is
  the chosen sweep mechanism.
- Parent death does NOT terminate children: orphans reparent to init and keep
  running (and holding pipes) — confirming the incident's orphan mechanism
  and the need for the settle-path sweep (incl. the clean-exit + pipe-holder
  class in AC12).
No design changes resulted.

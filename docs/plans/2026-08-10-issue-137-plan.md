# fix(subagent): worker exit termination, abort resilience, orphan cleanup — implementation plan (#137)

> **For Pi:** Use `executing-plans` to implement this plan task-by-task.

**Goal:** A `subagent` dispatch's progress display settles when the worker process exits — no endless "Working..." spinner after completion — and the completion is surfaced to the orchestrator so an Escape abort cannot lose a finished worker's output. Aborted-session MCP servers are reaped.

Three independent components: (1) per-task timeout + final `onUpdate` so the tool always returns and the spinner settles, (2) abort resilience — the abort handler is a no-op when the process already exited and partial results are returned instead of thrown, (3) result caching to disk + process-group cleanup for orphan MCP servers. ~180–260 line diff across `extensions/subagent/index.ts`, new test file, and new shared helper.

## Problem Statement

Three related defects in the subagent dispatch path (`extensions/subagent/index.ts`):

**Defect A — Endless spinner after worker exit (root cause: no per-task timeout + no final onUpdate).** The subagent tool's `execute()` Promise resolves when ALL workers in a batch (chain/parallel) finish. If one worker's process hangs (pi sub-agent deadlocked, MCP transport stall, infinite tool loop), the entire tool hangs. The orchestrator's "Working..." spinner runs indefinitely — the user cannot distinguish "worker done, tool waiting for sibling" from "worker stuck." This was observed in the tortoise batch session (Aug 8–10): workers #325 completed (merged PR tortoise#679 at 2026-08-08T21:39Z) but another worker in the batch hung, so the tool never returned.

Additionally, `runSingleAgent()` does NOT call `emitUpdate()` after `proc.on("close")` fires. The last `emitUpdate()` happens during the final `message_end` event, which may precede `close` by seconds. The core's streaming display never receives a "completed" state.

**Defect B — Escape abort loses completed worker results (root cause: race condition in killProc + unconditional throw).** `runSingleAgent()` registers an abort handler on the `AbortSignal`. On Escape, `killProc` sets `wasAborted = true` and kills the process. After `close` fires and the promise resolves, the code checks `if (wasAborted) throw new Error("Subagent was aborted")`. This throws UNCONDITIONALLY — even if the process had already exited with code 0 before the Escape. There's a race: `close` fires → promise resolves → but before `wasAborted` is checked, the Escape signal arrives → `wasAborted = true` → `killProc` is a no-op (process already dead) → but the throw still fires → result lost.

For chain/parallel modes, the throw propagates out of `runSingleAgent` without pushing the result to the accumulator — previously completed steps' results are lost. The user had to verify worker #325's PR merge via GitHub API because the tool returned only "aborted."

**Defect C — Orphaned MCP server processes after abort (root cause: SIGKILL bypasses process.on("exit") cleanup).** The subagent kill sequence is SIGTERM → 5s wait → SIGKILL. The mcp-client extension's cleanup (`process.on("exit")` handler that kills `transportPids`) fires during graceful SIGTERM shutdown — but only if all MCP server disconnects complete within 5s. The mcp-client has its own 5s disconnect timeout (`disconnectAll` → timeout → `[mcp-client] Disconnect from 'exa' timed out after 5000ms — forcing`). If the MCP disconnect cascades past the 5s window, SIGKILL fires before cleanup and MCP servers become orphans. Additionally, HTTP-based MCP transports (started via `npx` as separate processes) may be in different process groups and survive the subagent's process-group kill.

## Per-Component Design

### Component 1: Per-task timeout + final onUpdate (Defect A)

**Files:** `extensions/subagent/index.ts` — `runSingleAgent` (~L280–L340)

**Behavior contract:**
- New env var: `SUBAGENT_TASK_TIMEOUT_MS` (default: `1_800_000` = 30 min, same as `TASK_HEARTBEAT_TIMEOUT_MS`. Rationale: pi --mode json streams progress; a long implementation task (e.g., epic-executor worker) can legitimately take 20+ min. The heartbeat already prevents silence timeout; the task timeout is a hard cap for the "worker hung" case. Set to `0` to disable.)
- When timeout fires: kill the subagent process (SIGTERM → 5s → SIGKILL, same as abort), resolve with `stopReason: "timeout"`, exitCode = `null` (killed).
- After `proc.on("close")` fires AND after all buffered lines are processed: call `emitUpdate()` ONE final time before resolving the promise. This ensures the core's streaming display receives the final state.
- The timeout timer is cleared on `close` (alongside the heartbeat interval).

**Caller contract changes:**
- `isFailedResult()` adds `"timeout"` to its check: `stopReason === "timeout"` → failed.
- Chain mode: a timed-out step stops the chain (same as error/abort). Previous steps' results are preserved and returned.
- Parallel mode: timed-out tasks are recorded with `stopReason: "timeout"`. The tool returns all results (completed + timed-out).

**Timeout edge cases:**
- If `SUBAGENT_TASK_TIMEOUT_MS` is 0 or negative → no timeout (backward compat).
- If the process finishes within 5s of the timeout firing, the SIGKILL may race with natural exit. The `settled` guard (existing pattern from builtin-tools `spawnSubAgent`) prevents double-resolve: `if (settled) return; settled = true; resolve(...)`.

### Component 2: Abort resilience — don't lose completed results (Defect B)

**Files:** `extensions/subagent/index.ts` — `runSingleAgent` abort handler (~L420–L440), chain/parallel callers (~L370–L420)

**Behavior contract for `runSingleAgent`:**
1. `killProc` checks `if (proc.exitCode !== null) return;` before any kill action — if the process already exited, the abort is a no-op.
2. After `close`: if `wasAborted && exitCode === 0` → set `currentResult.stopReason = "completed_before_abort"` and return normally (do NOT throw). The result is valid; the abort arrived after completion.
3. If `wasAborted && exitCode !== 0` → set `currentResult.stopReason = "aborted"`, `currentResult.errorMessage = "Subagent was aborted (user-initiated)"`, and RETURN (do NOT throw). The caller receives a proper result record, not a thrown exception.
4. **`runSingleAgent` NEVER throws on abort.** It always returns a `SingleResult`.

**Behavior contract for chain mode:**
- Wrap each `runSingleAgent` call in try/catch (defense-in-depth; with F4 it should never throw, but network/OS errors still can).
- On any failure (including abort/timeout), accumulate results up to the failed step and return. Previous steps' results are in `details.results`.
- The returned `content[0].text` describes which step failed and includes previous outputs.

**Behavior contract for parallel mode:**
- Each `runSingleAgent` call inside `mapWithConcurrencyLimit` is wrapped in try/catch.
- All results are collected into `allResults[]` regardless of individual failure.
- The tool returns all results — completed, aborted, and timed-out.

**Behavior contract for single mode:**
- `runSingleAgent` result is returned directly. Aborted/timeout results carry `isError: true`.

### Component 3: Result caching (Defect B — defense in depth)

**Files:** `extensions/subagent/index.ts` — new `cacheResult()` helper, called from `runSingleAgent` after completion

**Design:**
- Cache directory: `~/.pi/agent/task-results/<dispatch-id>/`
- Dispatch ID: SHA-256 hash of `agent + task + timestamp`. Collision-tolerant (timestamp gives uniqueness).
- On each `runSingleAgent` return (whether success, failure, timeout, or abort): write the `SingleResult` as JSON to `<cache-dir>/result.json`.
- On abort signal: if any cached results exist for this session, the error details include the cache path so the orchestrator (or user) can recover.
- Cache files have a TTL: the agent or a cleanup job can delete entries older than 24h (not implemented in this plan — deferred to a janitor task).
- The cache write is fire-and-forget (no await on critical path) using `fs.promises.writeFile` in a non-blocking manner.

**Recovery path:**
- The orchestrator's prompt guidelines should instruct agents: if a subagent dispatch returns "aborted" or "timeout" with `details.cachePath`, read the cache file to recover completed results.
- No automatic recovery in this plan (the orchestrator is an LLM — it can read files).

### Component 4: Process-group cleanup (Defect C)

**Files:** new `extensions/shared/tree-kill.ts`, modified `extensions/subagent/index.ts`

**New shared helper: `extensions/shared/tree-kill.ts`**
```typescript
// tree-kill.ts — recursively kill a process tree.
// ponytail: single file, no dependencies beyond Node.js built-ins.
// Cross-platform: macOS (pgrep), Linux (pgrep), fallback to ps.

export function treeKill(pid: number, signal: NodeJS.Signals = "SIGTERM"): void {
  try {
    const children = getChildPids(pid);
    for (const childPid of children) {
      treeKill(childPid, signal); // depth-first: kill children first
    }
    process.kill(pid, signal);
  } catch {
    // Process already dead — ignore
  }
}

export function getChildPids(pid: number): number[] {
  // Try pgrep first (macOS + Linux)
  try {
    const result = execSync(`pgrep -P ${pid}`, { timeout: 2000, encoding: "utf-8" });
    return result.trim().split("\n").filter(Boolean).map(Number);
  } catch {
    // pgrep not available or no children
  }
  // Fallback: ps
  try {
    const result = execSync(`ps -o pid= --ppid ${pid}`, { timeout: 2000, encoding: "utf-8" });
    return result.trim().split("\n").filter(Boolean).map(s => Number(s.trim()));
  } catch {
    return [];
  }
}
```

**Changes to `runSingleAgent`:**
- Spawn subagent with `detached: true` to create a new process group.
- Track the PID.
- On abort or timeout: call `treeKill(pid, "SIGTERM")` instead of `proc.kill("SIGTERM")`. This recursively kills all children (MCP servers) before killing the subagent itself.
- The existing 5s SIGKILL fallback also uses `treeKill(pid, "SIGKILL")`.
- On natural `close`: no cleanup needed (the subagent's own `process.on("exit")` handler in mcp-client already handles it).

**Why `detached: true` is needed:**
Without `detached: true`, the subagent is in the same process group as the orchestrator. `process.kill(-pid, signal)` would send the signal to the orchestrator too. With `detached: true`, the subagent gets its own process group, and `treeKill` finds children via parent PID. We don't use process-group kill (`kill(-pgid)`) because MCP servers started via `npx` may create their own process groups — parent-PID-based tree traversal catches these.

**Orphan detection (best-effort, deferred):**
A janitor function could scan for processes whose parent PID is 1 (init) and match known MCP server patterns (e.g., `npx @anthropic-ai/mcp-server-*`). This is out of scope for this plan — the tree-kill on abort/timeout handles the common case; a separate housekeeping task can handle edge cases.

## Non-Goals (explicit)

1. **No changes to pi harness core.** The spinner rendering, Escape abort mechanics, and tool lifecycle are core concerns — we only ensure the extension returns promptly and caches defensively.
2. **No changes to the builtin-tools `task` tool.** The `task` tool (`extensions/builtin-tools/index.ts`) has its own sub-agent spawn path (`spawnSubAgent`) with its own timeout/retry logic. Its issues (#129 silence timeout) are tracked separately. The `subagent` tool in `extensions/subagent/index.ts` is the focus here.
3. **No automatic result recovery.** The orchestrator is an LLM — it can be instructed (via prompt guidelines) to read cache files. Building an automatic recovery loop is an orchestrator-level concern, not a tool-level one.
4. **No MCP server port tracking.** Tracking which ports MCP servers bind to and verifying their cleanup adds complexity disproportionate to the benefit. The tree-kill approach handles the common case; a separate housekeeping script can scan for orphans.
5. **No cache TTL janitor.** Cache entries are written and left for 24h. A cleanup job is deferred.
6. **No changes to `isFailedResult` semantics for non-abort consumers.** Only `stopReason` checks are extended; callers that don't inspect `stopReason` see no change.
7. **No heartbeat interval changes.** The existing 30s heartbeat in `runSingleAgent` is left unchanged — it prevents the orchestrator's silence timeout from triggering. The new per-task timeout is a separate, independent mechanism.

## Acceptance Criteria

1. On worker exit (any exit code, any stopReason), the tool's `execute()` Promise resolves. The tool NEVER throws "Subagent was aborted" — it always returns a `SingleResult` with the appropriate `stopReason`.
2. Per-task timeout (`SUBAGENT_TASK_TIMEOUT_MS`) kills hung workers and returns `stopReason: "timeout"`. Other workers' results are preserved (chain: previous steps; parallel: all tasks).
3. Escape after worker completion: the abort handler is a no-op (process already exited). The result is returned with `stopReason: "completed_before_abort"` (if abort arrived post-exit) or `"end"` (normal completion).
4. Final `emitUpdate()` fires after `proc.on("close")` so the core receives a terminal update.
5. Each completed result is cached to `~/.pi/agent/task-results/<hash>/result.json`. Aborted results include `details.cachePath`.
6. On abort/timeout, the subagent process tree (including MCP server children) is recursively killed via `treeKill`.
7. All existing tests (builtin-tools 31 tests, subagent-integration 6 tests, retry 12 tests, e2e smoke) stay green.

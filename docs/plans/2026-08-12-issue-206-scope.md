## 1. Problem-Diverge (framings + assumption map)

### Candidate framings

**F1 — "The hang is a stall-mechanics bug; fix #201/#202 only."**
The 105,150s hang is ultimately caused by gate interference stalling the
nested pi. Strength: targets the mechanical root cause; #201/#202 are already
tracked and this issue should not duplicate them. Weakness: the 29h wait was
a **decision failure** — the operator had no sanctioned abort point, no
timeout, no liveness signal to look at, and no documented recovery path.
Fixing stall mechanics alone leaves the launch side unbounded: the next stall
would still be waited out. Complementary, not competing — #201/#202 fix the
stall, #206 fixes the launch discipline.

**F2 — "A rule in docs is unenforceable; build a launch-wrapper script
(`scripts/run-bounded-pi.mjs`) that all launches must use."**
Strength: mechanical enforcement of timeout+log. Weakness: an agent can
equally ignore a wrapper (same trust model as docs — nothing forces the agent
to route through it); the wrapper adds a maintained surface (script + tests +
migration of every launch example); it cannot cover the user-side escape
(the one-liner runs in the human's terminal, outside any agent toolchain);
and it drifts into #208/#209 extension territory. Standard-tier doc issue
does not justify a new executable surface.

**F3 — "Agents won't read docs; put the rule in the extension (auto-inject
at session start)."**
Strength: enforcement at the point of failure, ambient for all sessions.
Weakness: explicitly out of scope per Align (#208/#209 territory); requires
runtime extension changes; this machine's `~/.pi/agent/skills` is a real-dir
mirror refreshed only on sync, so runtime-side changes propagate slowly; and
nested print-mode pi runs under the sequence-enforcer gate already have a
reduced extension surface (the Align run itself got gated). The issue is
scoped to docs + lint; enforcement machinery is a later, separate decision.

**F4 — Confirmed framing: launch-side rule gap.** No codified bounded-launch
rule, no documented liveness/abort discipline, and no sanctioned guard escape
exist anywhere in the three launch-path skills (research §1a/§1b: zero
bounded patterns in using-git-worktrees and subagent-driven-development; the
single background example in parallel-orchestrator has a log redirect but no
timeout/marker/abort). The fix: codify rule + bounded template + terminal
escape in the skills agents load at launch time, pinned by a drift-guard test.

## 2. Problem-Converge

**Confirmed problem:** The root cause of the 29h fleet hang is not only
stall mechanics (#201/#202) — it is the absence of a codified
bounded-launch rule, a liveness/abort discipline, and a sanctioned guard
escape at the fleet's nested-launch sites. Operators and agents have no
decision point that says "no liveness within N → abort", and no documented
recovery path; a silent wait is the only available behavior.

**Rejected framings:** F1 (mechanics-only — leaves the launch side unbounded;
complementary work already tracked), F2 (wrapper — illusory enforcement,
new surface, cannot cover the user-side escape), F3 (extension — out of
scope per Align, sync-lagged runtime).

**Falsification check:** If the confirmed problem were wrong, then bounding
launches would not change future incidents. Disconfirming evidence:
(a) the Align run itself — a nested print-mode pi under the gate — stalled
at research/scope steps with the same silence profile; (b) the incident
required a manual abort after ~29h, i.e., the failure included the absence of
an abort decision, which no stall-mechanics fix supplies. Would-be falsifier:
if, after this ships, a bounded launch (timeout + markers present) still
hangs the fleet because agents wait beyond N, that falsifies the rule's
*completeness* — it would justify F2/F3 as a follow-up (#208/#209), not the
rule's necessity.

**Confidence: 85/100** — all three indicator premises are repo-verified gaps;
the remaining 15 is the procedural-vs-mechanical limit (docs cannot
physically bound a launch; enforcement is a tracked follow-up, not a
rejection of this issue).

## 4. Solution-Converge — Chosen Approach: A (documentation-only + drift guard)

Selected by outcome, not file count: the two failure modes that actually
caused the 29h hang are (1) no bounded launch and (2) no abort decision —
both are *operator-facing* behaviors that only documented, enforced text can
change. B's enforcement is illusory (agent chooses whether to use the
wrapper), C's machinery cannot help the operator who needs the recovery
path. A is the only approach that delivers the user-terminal escape and the
self-checking abort trigger, in the repo's enforced-doc layer, with a drift
guard pinning all three indicators.

All three Align fold-ins are incorporated: (1) the one-liner is **added**
(absent today — research §1a), (2) timeout N = **30 min** is defined (§4.2),
(3) the abort trigger is codified (§4.1, sentence 3).

### 4.1 Exact rule text (canonical block — inserted in all 3 skills)

> **Never launch an unbounded nested pi.** Every nested or background `pi`
> launch MUST carry a hard timeout (30 minutes — the bounded-launch template
> below), a log redirect (`> /tmp/<launch-unique>.log 2>&1` — unique per
> launch; the template names it via `mktemp`), and a liveness
> marker — a `[task-heartbeat]` line written to the log at regular intervals
> (markers require `TASK_HEARTBEAT=1` AND `PI_MODE=print` set explicitly on
> the launch — the runtime writes them only when both are present; the task
> tool injects both, a manual nested launch must set them itself).
> Abort semantics: no marker within the window → the process is dead or
> blocked at the OS level → ABORT; markers present but no completion → the
> timeout is the bound — do NOT extend it. Note: marker presence ≠ progress —
> a gate-stalled pi keeps writing markers, which is exactly why the hard
> deadline is non-negotiable. On abort: kill the launch, surface the failure
> to the user, and never wait indefinitely — a silent wait is the failure
> mode this rule eliminates. The ONLY sanctioned guard escape is the terminal
> one-liner in `using-git-worktrees` (Guard Escape section), executed by the
> user in their own terminal — never by an agent tool, which the
> main-worktree guard blocks. When a bounded form is impossible, do not
> launch — escalate to the user instead.

Constraint check: the P0 phrase checked against the entire file
(`scripts/check-skill-lint.mjs:267`) does **not** appear in the rule text or
template — verified by grep, zero matches. No frontmatter keys are touched
(Risk B/C avoided).

### 4.2 Timeout value N — 30 minutes (1800 s)

Anchors (all repo-native):
- `extensions/subagent/index.ts:239` — `DEFAULT_TASK_TIMEOUT_MS = 1_800_000`
  (30 min), env-overridable via `SUBAGENT_TASK_TIMEOUT_MS` (the rule may note
  "explicit user override allowed; never the default").
- `extensions/builtin-tools/index.ts:14` — Tier-2 silence timeout: 30 min,
  driven by `[task-heartbeat]` markers on stderr.
- `extensions/task-heartbeat.ts:56` — marker cadence default 30s, so a
  healthy nested pi writes a marker within its first minute.
- `extensions/task-heartbeat.ts:77-79` — activation gate: markers emit only
  when `TASK_HEARTBEAT=1` AND `PI_MODE=print` AND
  `TASK_HEARTBEAT_DISABLE !== '1'` (the first two injected by the task tool —
  pi itself never sets `PI_MODE`); the template pins `PI_MODE=print` +
  `TASK_HEARTBEAT=1` explicitly for manual launches (F2; P4 — the disable
  check is also why acceptance 7's no-marker branch must set
  `TASK_HEARTBEAT_DISABLE=1` rather than rely on ambient env absence).
- Observed incident: 105,150s ≈ 29.2h — two orders of magnitude beyond any
  productive nested-pi task; N=30 min bounds 58× tighter while leaving
  generous headroom over the longest legitimate tool-call tiers (60s first-
  output / 30min silence).

Enforcement mechanism: a portable deadline watchdog — backgrounded `sleep
1800` + `kill -0` liveness probe, SIGTERM at 30 min, SIGKILL after a 60s
grace (see §4.3). NOT the GNU `timeout` binary, which does not exist on
macOS/Darwin (verified: not on PATH; no repo script uses it — F1/F8).

### 4.3 Bounded-launch template (canonical block — inserted in all 3 skills)

```
# Bounded nested pi launch — the ONLY sanctioned form of nested pi:
LOG="$(mktemp /tmp/nested-pi.XXXXXX)"
PI_MODE=print TASK_HEARTBEAT=1 pi -p "<prompt>" > "$LOG" 2>&1 &
launch_pid=$!
echo "launched $launch_pid → $LOG"

# Deadline watchdog — portable sleep-deadline + kill -0 liveness probe
# (no GNU timeout on macOS): SIGTERM at 1800s; SIGKILL after a 60s grace.
( sleep 1800; if kill -0 "$launch_pid" 2>/dev/null; then kill "$launch_pid"; pkill -P "$launch_pid" 2>/dev/null; sleep 60; kill -9 "$launch_pid" 2>/dev/null; fi ) &

# Liveness check + abort trigger — [task-heartbeat] markers land on stderr
# every 30s (2>&1 merged). No marker within 60s → the process is dead or
# blocked at the OS level → ABORT. Markers present → the launch is ALIVE and
# the 30-min deadline watchdog is the only remaining bound — do NOT kill here:
sleep 60
if grep -q '\[task-heartbeat\]' "$LOG"; then
  echo "ALIVE — bounded by the 30-min deadline watchdog"
else
  echo "NO MARKER — ABORTING (process dead/blocked at OS level)"
  kill "$launch_pid" 2>/dev/null
  pkill -P "$launch_pid" 2>/dev/null
  echo "ABORTED — surfacing to user"
  exit 1
fi
```

Semantics: the deadline watchdog is the primary guarantee — a backgrounded
`sleep 1800` with a `kill -0` liveness probe SIGTERMs the nested pi at
30 min automatically, so even a launch nobody watches is bounded; after a
60s grace it escalates to SIGKILL if the child ignores SIGTERM (portable
equivalent of GNU `timeout --kill-after=60 1800`, which does not exist on
macOS/Darwin — F1). `launch_pid=$!` is captured immediately after the pi
launch, before the watchdog is backgrounded, so the abort trigger still
targets the pi process, not the watchdog (micro-detail resolved — no wrapper
pid). `PI_MODE=print` and `TASK_HEARTBEAT=1` are both set explicitly on the
launch: the runtime emits `[task-heartbeat]` markers only when BOTH are
present (gate at `task-heartbeat.ts:77-79`; pi itself never sets
`PI_MODE` — only the task tool injects both, so a manual launch must set
them itself), and the liveness check would fail against a healthy pi if
either were missing (F2). The liveness
check + abort trigger are CONDITIONAL: the kill executes only when `grep`
finds no `[task-heartbeat]` marker in `$LOG` within 60s (round-2 F1 — the
previously unconditional `kill` right after the check inverted the rule and
contradicted §4.1's markers-present → timeout-is-the-bound); a healthy
launch that prints "ALIVE" is never killed at 60s — the 30-min deadline
watchdog is its only remaining bound. `LOG` is a per-launch temp file from
`mktemp` (round-2 F3): `$$` is the SHELL pid, so `/tmp/nested-pi-$$.log`
would collide across two backgrounded launches in one bash call, and
deriving the name from `${launch_pid}` inside the redirect is also wrong
(the redirect is evaluated before `$!` is captured). On abort — either
trigger (the 60s no-marker path or the watchdog's 30-min kill) — a
best-effort `pkill -P "$launch_pid" 2>/dev/null` reaps the launch's direct
children (BSD pkill exists on macOS); accepted limitation: grandchildren
may linger — a full tree-kill is an extension-side concern, out of scope
(round-2 F4). `2>&1` merges stderr so
`[task-heartbeat]` markers are inspectable in the log. The liveness check +
abort trigger codify Align fold-in 3.

conventions are `gtimeout` (coreutils via Homebrew) or the background +
`sleep`-deadline + `kill` watchdog pattern — the latter is what the canonical
template uses (already verifier-verified on this host). No design change.

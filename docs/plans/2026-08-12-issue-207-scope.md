## Diamond 1 — Problem

### 1.1 Problem-divergence (alternative framings)

**Framing A — "The real problem is hung processes; a marker won't help."**
The 29h incident was a HUNG nested-pi session; a hung process cannot issue
any tool call, so it can never `touch` a marker. Strength: true and
important — it correctly bounds the fix. Weakness: it erases the distinct
guard-blocked class (session alive and issuing tool calls, guard refusing
the recovery git ops / main-checkout edits needed to un-strand), which the
issue's own target T3 names ("Recovery git op allowed with marker, blocked
without"). The guard-blocked class is real, recurring (any main-checkout
session that needs to leave the hub: `git checkout main`, `git pull`,
branch recovery), and today is "escaped" only through an **undocumented
script-execution backdoor** (verified finding below) — there is no
sanctioned, bounded hatch.

**Verified finding (problem-verify round 1, F0):** a guard-blocked-but-
functional session DOES have a mid-session escape today: it can write
`/tmp/recover.sh` (write tool classifies ALLOW outside the project —
asserted in test.mjs: `check("/tmp file", "/tmp/foo.md", "ALLOW (outside
project)")`) and run `bash /tmp/recover.sh` (classifies `allow-non-git`),
executing arbitrary git ops unblocked. This is an **undocumented,
unbounded, unaudited script-execution backdoor** — not a sanctioned hatch.
**Scope decision:** DOCUMENT the backdoor in the guard README (do NOT
close it — closing risks false positives on legitimate script use);
closing is recorded as a possible follow-up, out of scope here.

Assumptions: [validated] hung processes cannot use a tool_call-based escape
(align challenge 2; nothing in the tool_call path runs for a hung process);
[validated] the hung-process class is out of scope here and currently
has NO owner — #203 EXISTS on GitHub and is CLOSED with a DIFFERENT scope
(auto-sync can't recover a main checkout stranded on a non-main branch —
not hung-process supervision); a process-supervision follow-up (new
issue) is required (round-2 F4).
Verdict: accepted as a **boundary**, not the problem.

**Framing B — "The guard should auto-allow recovery git ops when stranded."**
Detect stranding (main checkout + non-main branch or dirty tree) and
whitelist the recovery one-liner automatically. Strength: zero user action,
no new surface. Weakness: it violates the guard's explicit design invariant
— index.ts header: *"There is NO auto-bypass: the guard blocks every time,
so a rogue/parallel agent cannot retry its way past it."* A permanent
static whitelist hands a rogue/parallel agent exactly the retry path the
guard exists to deny; "stranded" detection is heuristic (a non-main branch
in main is precisely the parallel-work state the guard protects). The TTL
marker's whole advantage is that the window is **deliberate + bounded**.
Assumptions: [validated] no-auto-bypass is an explicit invariant
(index.ts:14-16); [unverified] that stranding can be detected without false
positives that break the guard's core promise. Verdict: rejected.

**Framing C — "Mid-session env injection via a pi-native command instead of
a file."** A session-native hatch (user types a pi command / agent sends a
message the extension intercepts; extension flips the bypass for that
session). Strength: session-scoped by construction, no filesystem backdoor,
no TTL needed. Weakness: a pi-native command is **pi-runtime-bound** — it
works only where the pi extension host is loaded (not for nested pi
sessions without the extension, and a Claude Code hook would need
separate wiring — round-2 F7: no PreToolUse hook artifact exists in-repo
or in ~/.pi/settings.json; the marker FILE is harness-agnostic only in
principle — only this pi extension implements the check/stamp, and its
absence is fail-safe), whereas the file marker is creatable by a human
terminal (F1/E rationale); and the file marker is the only mechanism
usable **without a human present and by non-pi actors** mid-session
today. (Earlier draft claimed "no command-hook precedent — the fleet is
tool_call-only": WRONG — loop-enforcer implements `/loop` session commands
via `pi.on('input')` (index.ts:1198), and `pi.registerTool` has SEVEN
in-repo precedents: loop-enforcer:644, builtin-tools, design-reviewer,
vision-interceptor, subagent, mcp-client, carousel-designer. The
mechanism exists; the rejection rests
on the harness-agnosticism grounds above, same as framing E, F2.)
Assumptions: [unverified] pi exposes a mid-session extension command
hook — mechanism precedents exist (`pi.on('input')`, `registerTool`) but
session-scoping semantics are unproven; [validated] file markers are
provably reachable (test.mjs asserts `~/.pi/...` writes classify ALLOW —
outside project; `touch` classifies allow-non-git). Verdict: rejected as
the mechanism; noted as a possible future native improvement.

**Framing D — "Human-in-the-loop TUI approval."** The one-touch gesture
routes through `ctx.ui.confirm` (pi docs extensions.md:63-73 Quick-Start
pattern; in-repo precedent subagent/index.ts:692, gated on `ctx.hasUI` at
:679), and the bypass activates only on explicit human approval.
Strength: a real human authorizes every escalation; no marker file, no
TTL needed; the strongest possible audit. Weakness: **unattended recovery
is the incident's shape** — a human is not reliably present when a
session strands (the 29h incident ran unattended); the escape would be
unavailable exactly when needed. Assumptions: [validated] a human is not
reliably present at escalation time (incident evidence); [unverified]
`ctx.hasUI` is true for the sessions that strand. Verdict: rejected as
the mechanism; kept as an optional future enhancement (see Decision 2
risk note — one-time `ctx.ui.confirm` when `ctx.hasUI`).

**Framing E — "A registered custom tool via `pi.registerTool`."** The
guard exposes an escape tool (e.g. `allow_main_edits` with a reason
parameter) the agent can call mid-session. Strength: session-scoped by
construction, typed parameters (reason), no filesystem surface.
Weakness: pi-runtime-bound — the tool exists only inside pi sessions
loaded with the guard; it fails for nested pi sessions without the guard
and would need separate wiring for a Claude Code hook (round-2 F7: no
PreToolUse hook artifact exists — the marker FILE is harness-agnostic
only in principle; absence of a twin hook is fail-safe); it cannot be
created by a human terminal (the incident's operator escape); no TTL by
construction.
Assumptions: [validated] SEVEN in-repo `registerTool` precedents
(loop-enforcer:644, builtin-tools, design-reviewer, vision-interceptor,
subagent, mcp-client, carousel-designer — round-2 F5); [validated] the
marker FILE is harness-agnostic in principle (creatable by a human
terminal, TTL-bounded, no pi-runtime dependency); NOT validated as a
working non-pi check: only this pi extension implements the
check/stamp — a Claude Code hook would need separate wiring and is not a
critical dependency (absence is fail-safe, round-2 F7). Verdict:
rejected as the mechanism.

### 1.2 Problem-convergence

**Confirmed problem:** A guard-blocked-but-functional session — alive,
issuing tool calls, sitting in the shared main checkout where the guard
blocks destructive git ops and main-checkout edits — has **no sanctioned,
bounded mid-session escalation path**. The only hatch reachable today is
an **undocumented, unbounded, unaudited script-execution backdoor**: the
session writes `/tmp/recover.sh` (write tool: ALLOW outside project,
asserted in test.mjs) and runs `bash /tmp/recover.sh` (`allow-non-git`)
to execute arbitrary git ops unblocked. The env hatch
(`AGENT_ALLOW_MAIN_EDITS=1`) is fixed at session start and cannot be set
on a running process. So: no **sanctioned** hatch exists, and the only
escape is an unbounded bypass with no audit. **The marker upgrades an
unbounded bypass into a bounded (15-min TTL), audited, session-scoped
one.** (Reframe per problem-verify F0: the literal "no mid-session
escalation path" claim was FALSE — falsifier #2 fires against the literal
statement; the reframed problem survives it.)

- The escape must be **mid-session reachable** (a tool-callable gesture,
  not env), **deliberate, audited** (agent-initiated with an audit
  record; NOT user-approved — see Decision 2 risk note, F8), **bounded**
  (not permanent), and **auditable** (a record of who/why).
- Out of scope, explicitly: hung processes (no tool calls possible — the
  hung-process class currently has NO owner: #203 is CLOSED with a
  different scope (auto-sync non-main-branch recovery, not process
  supervision); process-supervision follow-up (new issue) required,
  round-2 F4); closing the script-execution backdoor (documented in the README
  instead; closing is a possible follow-up, F0); parallel-session
  collisions (the guard stays enforcing for everyone else);
  agent-infra's own main checkout (already exempt via
  `isAgentInfraRepo()`).

**Rejected framings:** A (hung processes — NO current owner: #203 is
CLOSED with a different scope (auto-sync non-main-branch recovery, not
process supervision); process-supervision follow-up (new issue) required,
round-2 F4; documented in the README/skill so the boundary is explicit);
B (auto-allow — violates the no-auto-bypass invariant, hands rogues a
permanent whitelist); C (pi-native command — the surface EXISTS
(`pi.on('input')` loop-enforcer:1198; `pi.registerTool` seven in-repo
precedents — round-2 F5) but a pi-native hatch is pi-runtime-bound, not
harness-agnostic — F2; kept as a documented future option); D
(human-in-the-loop `ctx.ui.confirm` — a human is not reliably present at
escalation time, F1; kept as an optional future enhancement); E
(registered custom tool via `pi.registerTool` — pi-runtime-bound, not
creatable by a human terminal, no TTL by construction, F1; rejected).

**Falsification check:** If every guard-blocked session could cheaply
restart with the env var, the problem would be empty — it can't: restart
loses conversation context and requires human action, and the stranded
session already holds the context needed for recovery. Falsifier #2 — "a
mid-session hatch already exists" — **FIRES against the literal
statement** (F0): the `/tmp/recover.sh` + `bash` backdoor is reachable
mid-session, so "no escalation path" is false. The REFRAMED problem — no
*sanctioned, bounded, audited* hatch exists; the only escape is an
undocumented, unbounded, unaudited backdoor — survives falsifier #2: a
bounded, audited, session-scoped hatch is genuinely absent. Both
falsifiers fail to fire against the reframed problem.

**Confidence: 85/100** — the problem is directly evidenced by the incident,
the code confirms both the gap (single env check at index.ts:52-55, 95, 240)
and the reachability (outside-project writes allowed — the same property
that powers the undocumented backdoor, F0), and the boundary is drawn
(the hung-process class has NO owner — #203 is CLOSED with a different
scope, round-2 F4). Residual uncertainty: how often the
guard-blocked class occurs without human assistance is anecdotal
(frequency data unverified).

## Diamond 2 — Solution

### 2.1 Solution-divergence

**Approach A — TTL'd file marker, pure functions, guard-stamped session id
(the issue's approach, with the align conditions resolved).**
`~/.pi/agent/.allow-main-edits` (dotfile precedent `.mcp.json`); mtime-based
15-min TTL; pure dependency-injected functions in classify-git.mjs
(`isAgentInfraRepo(cwd, env)` precedent); creation logged to the shared
audit log; docs in a new guard README + using-git-worktrees skill.
Strengths: provably reachable mid-session (one `touch` = allow-non-git,
outside-project); slots beside the existing per-tool_call env check with
zero architectural change; bounded + audited + session-scoped; fully
unit-testable with fake stats. Weaknesses: new filesystem surface (any
same-user process can touch — bounded by TTL, contained by session-scoping,
logged); mtime forgeable (`touch -d`) — accepted same-user trust bound.

**Approach B — Marker with mandatory reason content; `touch` alone is
insufficient (creation requires `printf '<json>' > marker`).** Strength:
reason is enforced structurally, not just documented; a bare `touch`
(accident or the cheapest rogue gesture) activates nothing. Weaknesses:
breaks the issue's documented "one `touch` command" claim; the agent
creating the marker does not know its own session id (it lives in the pi
ctx, not the shell), so the content-writer cannot fill `session_id`
without extra plumbing — this is exactly why the guard must stamp the id
itself; a `printf`/redirect that clobbers the file also clobbers the
stamp, creating a write-ordering race the docs would have to explain.
Verdict: the reason requirement is right and is folded into A (stamp
preserves/accepts a reason; audit carries it); the "printf-only" mechanism
is rejected.

**Approach C — Whitelist a single recovery one-liner when stranded
(`git checkout main && git pull --ff-only`).** Strength: simplest possible
recovery gesture for the incident's exact shape. Weaknesses: hardcoded
command is brittle (recovery ops vary: stash, restore, branch recovery);
a whitelisted command is a **permanent, non-TTL'd bypass** — worse than a
bounded marker; any parallel/rogue session inherits it; duplicates the
auto-allow flaw of problem-framing B. Verdict: rejected.

### 2.2 Solution-convergence — chosen approach

**Chosen: Approach A** — TTL'd file marker in `~/.pi/agent/.allow-main-edits`
with guard-stamped session scoping, pure logic in classify-git.mjs, shared
audit logging, and both doc deliverables. All align conditions resolved as
follows.

#### Decision 1 — TTL semantics (align condition 3): pinned

- **Clock: mtime** (`Date.now() - statSync(marker).mtimeMs`), the
  loop-enforcer `MANIFEST_MTIME_WINDOW_MS` precedent
  (index.ts:1292-1293, 1328-1329). Metadata-only re-read; `touch`
  naturally refreshes the window — the documented one-touch command stays
  a literal one-liner.
- **Constant:** `ALLOW_MAIN_EDITS_MARKER_TTL_MS = 15 * 60 * 1000` in
  classify-git.mjs (named, exported, single source of truth).
- **NOT env-overridable.** The TTL is a security parameter; an env override
  is a second, invisible weakening knob the fleet would have to audit.
  Precedent: loop-enforcer's window is a hard constant too. Testability is
  served by the function signature — `isAllowMarkerActive(stats, nowMs,
  ttlMs)` injects both time and TTL — so no env surface is needed.
- **Comparison: strict `<`** — `(nowMs - st.mtimeMs) < ttlMs`; a marker
  exactly TTL old is expired (boundary tested both sides).
- **Refresh: `touch` again** (mtime refresh, content preserved by the
  guard's re-stamp). Re-touching restarts the window; tested.
- **Re-read per tool_call, never cached.** No module-level marker state;
  `statSync` + one small `readFileSync` per gated event (both trivial;
  slack-bridge reads its owner-lock every poll; loop-enforcer stats
  manifests in hot paths). Proven by the stale-mtime integration test
  (see §2.3): the same read function returns different results for the
  same path across a `touch` — impossible with any cache.
- **Future mtime** (clock skew / `touch -d`) passes (negative age < TTL) —
  documented as an accepted same-user trust bound, same as `touch -d`
  forgery generally.

#### Decision 2 — Parallel-session leakage (align condition 1): session-scoped, guard-stamped

**Session-scoped, not documented-acceptance.** The issue's I3 claim "never
applies to parallel sessions automatically" is made **literally true** by
embedding the creating session id — and the **guard stamps the id at
creation**:
- **Session-id source (F3, corrected round-2 F1/F2):** `process.env.PI_SESSION_ID ?? ctx.sessionManager?.getSessionId()`
  — env first. `PI_SESSION_ID` is verified exported in pi sessions
  (constant per process; NOT inherited by subagents — round-2 F1: pi
  only writes it into bash-tool child envs, the extension-host
  process.env is never assigned it, so a print-mode subagent's value is
  its OWN session id). The `ctx.sessionManager` fallback IS proven in a
  tool-invocation context (round-2 F2, corrects F3): loop-enforcer's
  `getSessionId` helper (index.ts:52-54) is invoked with ctx in its
  `pi.registerTool` callback (loop-enforcer:668 and :922), plus
  `before_agent_start` (1494), `agent_end` (1586), `session_shutdown`
  (2012) — only the `pi.on('tool_call')` handler (index.ts:1576) ignores
  ctx. Env-first design kept. Guard-stamping uses the same expression.

- When the per-tool_call handler sees a bash command that targets the
  marker path (`isAllowMarkerCommand`), it writes the marker content
  `{"session_id": <current>, "reason": <from command comment or existing
  content>, "ts": <ISO>}` — where `<current>` =
  `process.env.PI_SESSION_ID ?? ctx.sessionManager?.getSessionId()` (F3)
  — **before** allowing the command. `touch` then updates mtime and
  preserves content — no ordering race, because `touch` never rewrites
  content. Stamp write is try/catch-wrapped, fail-silent (F7, Decision 6).
- **Read-side match:** active ⟺ mtime fresh AND content parses AND
  `session_id === current session id` (same F3 expression on the read
  side). Absent / unparseable / missing session_id / mismatched / null
  current id (headless sessions: no env, no ctx) → **inactive → block**
  (fail-safe).
- **Delegation (round-2 F1, corrects F4):** print-mode subagents do NOT
  inherit the parent's `PI_SESSION_ID` — pi only writes it into bash-tool
  child envs, and the extension-host process.env is never assigned it, so
  a subagent's `PI_SESSION_ID` is the SUBAGENT'S OWN session id. The
  marker is **per-process-session-scoped**: each session (parent and any
  subagents) gets its own independent window via its own stamp. Two
  consequences, documented in the README: (1) a subagent's touch is
  stamped with the subagent's id → the parent's read-side match fails →
  the parent stays blocked — **delegation recovery does NOT work**;
  recovery must run in the session that created the marker; (2) per the
  containment rule, a subagent re-touching an active marker RE-SCOPES it
  to the subagent's id, revoking the parent's window (fails-closed for
  the parent). Headless sessions with a null id (no env, no ctx) cannot
  escalate (F9). **Plan-gate verification step:** live two-process test
  confirming `PI_SESSION_ID` identity in a spawned print-mode subagent
  (assert subagent id ≠ parent id).
- **Containment result:** a parallel session's `touch` is stamped by *its*
  guard with *its* id → the marker re-scopes to the toucher and the first
  session is blocked again. Rogue-process `touch` (never observed by a
  guard) leaves no content → unscoped → inactive. The only residual hole —
  a rogue re-touching an already-stamped marker extends the stamping
  session's window — is inside the accepted same-user trust bound (same
  user can already kill/steal the session) and still bounded by TTL +
  audit.
- **Rogue-agent trade, explicit (F8):** this is NOT a user-approved
  mechanism — the agent self-escalates with one touch and audit is
  after-the-fact. The trade: same-user trust (a rogue process is already
  outside the threat model — same user can kill/steal the session), TTL
  (15 min, re-read per tool_call), and audit (every activation recorded
  with session_id + reason). All scope/README language says
  **"deliberate, audited"**, never "user-approved". Optional future
  enhancement, NOT in scope: a one-time `ctx.ui.confirm` before the
  first stamp when `ctx.hasUI` (pattern: subagent/index.ts:679, 692).
- **Session-scoped, repo-agnostic (F10f):** one marker window covers ALL
  repos the session touches (the hub and any worktrees) — accepted and
  documented.
- **The one-touch command is preserved**: `touch ~/.pi/agent/.allow-main-edits`
  (+ optional trailing `# reason...` comment, extracted into the audit and
  the content). A `printf`/`echo`/redirect to the marker path is
  **out-of-contract**: it clobbers the stamp, the marker becomes unscoped,
  and the guard blocks — documented fail-safe behavior, not a supported
  flow.

#### Decision 4 — Marker path + content + creation command

- **Path:** `join(homedir(), ".pi", "agent", ".allow-main-edits")` —
  derived from `os.homedir()`, never hardcoded (shared/audit-log.ts:42
  convention); consistent with the fleet state root (research §4).
- **Path guard:** `isAllowMarkerPath(path, home)` — exact-match after
  `resolve()`; traversal/sibling candidates rejected.
- **Tilde / `$HOME` expansion (F5):** `isAllowMarkerCommand` extracts the
  token from the bash command, expands `~` and `$HOME` (including quoted
  variants like `"$HOME/..."`) BEFORE `resolve()` + exact-match via
  `isAllowMarkerPath` — so `touch ~/.pi/agent/.allow-main-edits` and
  `touch "$HOME/.pi/agent/.allow-main-edits"` both classify as marker
  commands. Tested (quoted + `$HOME` variants).
- **Symlink defense (F6, firing form pinned — round-2 F3):** `statSync`
  follows symlinks, so `isSymbolicLink()` on the stats object never fires
  in production — the branch is DROPPED from the pure check. The SOLE
  symlink defense is a **realpath equality check in index.ts, fail-safe**.
  The earlier wording ("`realpathSync(marker)` must equal the realpath of
  the expected location") was a TAUTOLOGY: the path IS the expected
  location, so both sides resolve identically even for a symlinked
  marker. PINNED firing form: **block when
  `realpathSync(markerPath) !== resolve(markerPath)`** — reject ANY
  symlink indirection (`~/.pi/agent` is not a symlink in this fleet); a
  symlink pointing elsewhere (or a broken link — realpathSync throws) →
  mismatch/throw → absent → block. Pure function carries no symlink
  branch; test coverage moved to integration case 20 (production path).
- **Content:** one JSON line `{"session_id","reason","ts"}`; written by
  the guard at stamp time; `parseAllowMarker(content)` → object | null;
  null → inactive.
- **Creation command (canonical):** `touch ~/.pi/agent/.allow-main-edits`
  — classifyGitCommand → `allow-non-git`; outside-project write path →
  ALLOW (test.mjs precedent). Reason variant:
  `touch ~/.pi/agent/.allow-main-edits  # recovery: stranded main`.
- **Refresh:** re-run the same `touch` (extends the window; re-stamps
  idempotently).
- **One command per touch (F10c):** `touch ... && git checkout main ...`
  in a SINGLE bash call does NOT work — the guard classifies the whole
  command before any stamping occurs, so the git part is blocked and the
  touch never executes. `touch` must be its own command; the recovery git
  op goes in the FOLLOW-UP call. Stated in README + skill + acceptance
  scenario 2.

#### Decision 6 — Fail-safe behavior

- Absent / unreadable (statSync or readFileSync throws) / expired /
  unparseable / unscoped / mismatched / symlink

## External validation (Perplexity research, 2026-08-12)

The TTL'd marker design mirrors sudo's credential-timestamp model, the industry
standard for bounded privilege escalation:
- Per-user timestamp file + `timestamp_timeout` (TTL) + `tty_tickets`
  (per-session scoping) + syslog audit — sudo docs (sudo.ws sudoers.man,
  sudoers_timestamp.man).
- Documented anti-pattern: unbounded/infinite timestamp windows increase
  exposure to anything running in the session (askubuntu "sudo password
  timeout infinite") — avoided here via the fixed 15-min TTL (non-overridable
  by design).
- Our per-process-session scoping is the direct analogue of `tty_tickets`
  (separate record per terminal/session).
No design changes resulted; this validates session-scoping + TTL + audit as
best practice, not an invention.

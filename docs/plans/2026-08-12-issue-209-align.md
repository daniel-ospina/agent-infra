## Stage 1 — Align (standalone, adversarial-lite)

### O/I/T alignment check

**Objective** — coherent and measurable. "Background work doesn't collapse
under load storms; load storms don't silently kill live work" maps cleanly to
the three indicators (watchdog bounds, batch suspension policy, env-overridable
timeouts) and the two targets.

**Indicator 1 (watchdog bounds scale with load)** — feasible and well-anchored.
`extensions/builtin-tools/index.ts` already carries `toolsInFlight` /
`turnActive` / `streamAgeMs` in `HeartbeatState` and routes all kill clauses
through one pure decision function (`heartbeatKillDecision`), so a
"don't cut with toolsInFlight>0" exemption and a load-scaled first-message
bound are localized, unit-testable changes. Live in-repo evidence of the exact
failure class: while this align run was being written (2026-08-12), an
exploration sub-agent was cut by the 300s first-message clause (738s silence,
bound 300s) during a tool-heavy turn — the #198 recurrence this indicator
targets.

**Indicator 2 (documented fleet policy: suspend background batches when
loadavg > threshold)** — gap: **no loadavg code exists anywhere in agent-infra**
(scripts/, extensions/, docs/ — zero references to loadavg, `/proc/loadavg`,
or `os.loadavg()`). The wt-291 gated-rerun script the issue cites is NOT in
agent-infra (candidate location: the tortoise repo, wt-291 being a tortoise
issue) — "promote to a shared helper" is therefore a **cross-repo extraction**,
and agent-infra has no batch-scheduling scripts at all (`scripts/` inventory
has no cron-wrapper/rerun/batch dispatchers; `swarm-org.mjs` is an org-data
client, not a scheduler — the "swarm operations scripts" surface lives in the
swarm repo). Scope must pin: where the helper lives (agent-infra
`scripts/`/`extensions/shared/` as the shared home), how swarm cron wrappers
consume it, and the wt-291 extraction provenance (S10 licensing precedent).

**Indicator 3 (test-timeout constants env-overridable with load-aware
defaults)** — pattern already proven in-repo: `TASK_FIRST_MESSAGE_MS`
(builtin-tools/index.ts:461) and the other `TASK_*` knobs are env-overridable
with clamped defaults. The 2s git-lookup timeout from #196 needs locating at
research (candidate: `extensions/shared/`), but the mechanism is
uncontroversial.

**Gaps to resolve at Scope (not blockers):**
1. **'Load' is undefined.** Issue never states the signal or units. Proposal:
   `os.loadavg()[0]` (1-min, portable macOS/Linux, no new deps) with an
   injectable getter so T1's "load 60+" test is a unit test, not a CI load
   generator. cgroup quotas / CPU steal are invisible to loadavg — acceptable
   for a same-host fleet (the 2026-08-12 storm was host-level and loadavg-visible)
   but must be documented.
2. **Suspend threshold unspecified.** wt-291's "< 25" was load 25 on 10 cores
   (2.5×). Loadavg is raw, not per-core — a fixed constant means different
   things on different hosts. Need default + env override + hysteresis
   (single-sample thresholds thrash: suspend/resume churn costs more than it
   saves).
3. **Supersede semantics vs #196/#198.** Issue says this "supersedes #198's
   static bound" — the plan must state explicitly whether the static bump is
   removed, replaced, or layered, so no regression of shipped fixes.
4. **Defer ≠ lose.** Target says batches "defer until load < threshold" — safe
   by construction only if the cron wrapper actually resumes; an exit-on-high-load
   wrapper with no resume mechanism silently never runs the batch (worse than
   running under load). State the resume mechanism.
5. **Observability.** Log bound extensions / suspension events so T2 is
   verifiable in production without waiting for a real storm.

### Adversarial challenge A — "loadavg is the wrong signal / simpler alternative"

Strongest case against: loadavg is blunt (trailing, host-wide, inflated by
steal in VMs, blind to cgroup quotas), and the *watchdog* half of the failure
needs no load-sensing at all — the kill already resolves `undefined`
(retryable), so a cut under load is auto-retried, and a static generous bound
plus a `toolsInFlight>0` exemption (6h tool-stall still bounds it) closes #198
without reading the system. Verdict: **partially valid** — the watchdog fix
should be static + toolsInFlight-exemption first (cheap, zero new signal
sources); load-sensing earns its keep mainly for *batch deferral* (avoids
compounding load — the 10x slowdown — which a static watchdog bump cannot do)
and for first-message patience scaling. Not a reason to skip; a reason to
sequence and keep the load-aware default modest.

### Adversarial challenge B — "what assumption is it betting on?"

It bets that (a) loadavg reflects the pi host's own contention — true for
same-host sub-agents and host-level storms like 2026-08-12, false for
container/VM throttling (quota-capped but loadavg-low → watchdog still cuts;
neighbor load → false batch suspension); (b) thresholds won't thrash — false
without hysteresis on single 1-min samples; (c) suspending is safe — only if
the scheduler persists/resumes, per gap 4; and (d) the storm class recurs —
its root cause (tortoise #1005 redislite leak) is being fixed separately, so
this hardens against a largely-eliminated trigger. Counter-evidence: BGSAVE
runs *routinely* (`scripts/daily-backup.sh` triggers it daily), leaks can
recur, and other bursts (builds, git clones) raise load too — "assume idle
load" is the wrong default regardless of #1005. Confidence in the premise:
medium-high; the issue's defensive value stands even if the specific trigger
is fixed.

### Eisenhower placement

**Important + Urgent — Do Now.** The failure class recurred live this week
(2026-08-12 storm: 10x suite slowdown, 3/3 sub-agents cut, #196 git-lookup
flake) and even recurred *during this align run* (sub-agent cut at 738s vs
300s bound). The fleet operates continuously and bgsave events are routine,
not freak. Fix is bounded (one extension decision function + one shared helper
+ env defaults) relative to the cost of a fleet collapse; deferring leaves live
work at risk each time host load spikes.

### Align decision

**CONDITIONAL-GO.** The watchdog half (toolsInFlight>0 exemption + scaled
first-message bound + env-overridable timeouts) is an unconditional, low-risk
win on proven machinery — proceed on that regardless. The load-sensing half
proceeds under three conditions resolved at Scope: (1) load signal = injectable
`os.loadavg()[0]` with hysteresis and an explicit per-host/default threshold
(and its interplay with #196/#198 stated — supersede, not regress); (2) shared
load-gated helper home = agent-infra, wt-291 extraction provenance confirmed
and swarm cron wrappers' consumption surface pinned (including a resume
mechanism so defer never silently drops a batch); (3) targets tested via
injected load values in `heartbeatKillDecision` unit tests + the helper's
threshold logic — no real-load CI generator required.

## Stage 1 — Align (standalone, adversarial-lite)

**Eisenhower:** Important + Not Urgent (Schedule). Follow-up to #209 — main's
`loadScaledBound` (#225) covers storms present AT SPAWN only; a storm starting
mid-dispatch leaves the static bound in force and a legitimately-slow agent is
still cut.

**Adversarial challenges:**
- A: "Just raise the static bound instead of per-tick scaling." A flat raise
  extends the cut latency for EVERY dispatch (incl. idle-load ones); per-tick
  scaling with a monotonic latch extends only when load is actually high and
  never shrinks below the run's high-water mark (no post-storm re-cut).
- B: "Per-tick recompute risks the bound SHRINKING right after a storm (the
  original #209 P1)." That P1 is exactly why the latch is the core of this
  change: the effective bound is monotonic per dispatch — it only ever grows.

**O/I/T sound:** YES — verifiable with multi-tick E-series tests (load1=60
mid-run → bound extends; load1 drops → latched, no re-cut); default 0/off
preserves existing assertions.

**Verdict: GO.**

## Stage 3 — Scope (design from 2f010b6, verified)

**Confirmed problem:** a load storm that starts after spawn does not extend the
first-message bound — mid-dispatch storms still cut legitimately-slow agents.

**Approach (recover 2f010b6's load-scaling implementation, rebase onto main):**
1. `HeartbeatDecisionInput` gains `load1` (default 0 → scale inert, legacy
   identical; 1000+ existing assertions preserved).
2. Per-dispatch monotonic high-water-mark latch of the effective bound:
   `effM = max(M, M × scale(load1_t))` latched per run — recomputed each 10s
   tick from live load (injectable `getLoad1()`), never shrinking below the
   run's max; cap 3× (900s).
3. `[task]`-prefixed bound-extension log (e.g. `[task] first-message bound
   300s → 900s (load1=60)`) on increase — production observability.
4. Wire into main's per-tick decision loop (replacing the spawn-time const
   `firstMessageMs` evaluation). SCALE FUNCTION (verifier P2 decision): reuse
   main's already-merged `loadScaledBound(baseMs, load)` as the scale fn
   (bands 1x/2x/3x, tested by #225) instead of re-introducing 2f010b6's
   per-core `scaleFirstMessageMs` — the latch + per-tick evaluation are the
   deltas; the scale fn stays main's (consistency, no semantic fork).

**Wiring check:** builtin-tools/index.ts + builtin-tools.test.ts; no other
surfaces (slack-bridge stays #232's; load-gate.mjs stays #251's).
**Complexity:** standard (builtin core).

## Stage 1 — Align (standalone, adversarial-lite)

**Eisenhower:** Important + Urgent (Do now). The 2026-08-11/12 incident cost a
29h hung nested-pi session because the guard's only escape hatch
(`AGENT_ALLOW_MAIN_EDITS=1`) cannot be set on a running process — a stranded
main checkout is currently unrecoverable by agents without human terminal
intervention. Frequency is low but each occurrence is fleet-paralyzing
(shared hub), the fix is small (one extension + tests + docs), and the
incident context is fresh; complements #203 which covers the auto-heal path.

**O/I/T alignment check:**

- **Objective** is coherent and measurable: a mid-session, deliberate,
  bounded escalation path. It is the missing runtime half of the escape
  hatch (env-only = session-start-only). Good.
- **I1** (marker checked alongside `_isAllowMainEdits()`; TTL window) —
  specific and testable. Gap: the 15-min TTL is a DESIGN CHOICE, not a
  target — pin the constant (and decide env-overridability) at the Scope
  gate.
- **I2** (creation logged with reason; expiry re-read per tool_call, not
  cached) — correct design and testable. The per-tool_call re-read must be
  asserted in tests via a stale-mtime fixture (proves no caching); without
  that test the TTL is dead weight.
- **I3** (documented in guard README + using-git-worktrees) — GAP: there is
  **no `extensions/main-worktree-guard/README.md` today**; the target must
  name the concrete file (create README.md or extend an existing doc). The
  doc claims ("one touch command", why it expires, parallel-session
  behavior) are untested text — add drift-guard source assertions (the repo
  convention for skill/docs claims) or at minimum a manual verification
  checklist item.
- **Target T2 wording gap:** "never applies to parallel sessions
  automatically" is misleading — a user-level file in `~/.pi/agent/` is
  machine-global, so a parallel session on the same user/host within the TTL
  WOULD also be allowed. Must be re-scoped: either session-scoped (marker
  records its creating session id; guard matches) or explicitly documented
  as "machine-wide within TTL, creation is deliberate + audit-logged".
- **Feasibility confirmed** against the current code: the write/edit guard
  allows paths outside the project root (test.mjs asserts `~/.pi/...` →
  ALLOW (outside project)), and `touch` classifies as allow-non-git — a
  stranded session can create the marker today. `_isAllowMainEdits()` is
  already evaluated per tool_call event, so a per-event marker read slots in
  beside it with no architectural change.

**Adversarial challenge 1 — "Cheapest fix isn't a file; why not a
session-native or one-shot hatch?"** Alternatives: (a) a pi-native command or
extension-handled message (e.g. `!allow-main-edits <reason>`) — session-scoped
with zero new filesystem backdoor; (b) the guard whitelisting the single
designated command `touch ~/.pi/agent/.allow-main-edits` so no new check
surface exists at all. The file marker adds real attack surface: ANY process
running as the same user (including a rogue/parallel agent or any script) can
`touch` it and obtain a 15-minute window of main-checkout write +
destructive-git allowance, where today's env var requires a deliberate,
visible session start. Counter: this repo's pi extensions are tool_call-only
(no command-hook precedent verified — ⛔ superseded by scope F2:
`pi.on('input')` /loop and `pi.registerTool` precedents exist), so a
session-native hatch is unproven;
the file is the only mechanism provably reachable mid-session; TTL +
per-tool_call re-read + audit logging bound the window; and the design MUST
fold in a session-scope mitigation (marker records creating session id) so
the parallel-session leak is contained rather than waved at in docs.
Alternatives (a)/(b) rejected for unproven extension surface / narrower but
equivalent complexity; (b) is a viable fallback if session-scoping proves
ugly.

**Adversarial challenge 2 — "It bets that a stranded session can write the
marker and that expiry is enforced."** Both halves need scrutiny. (1) The
stranded session CAN write the marker (outside-project writes are allowed by
design — verified in test.mjs), but if the failure mode is a HUNG process
(the actual 29h nested-pi case), the session cannot issue any tool call at
all and the marker is useless — this issue fixes the guard-blocked class,
NOT the hung-process class, and must say so (that gap belongs to #203 /
process supervision). (2) Expiry is only as good as the per-tool_call
re-read: if implemented as a session-start stat or cached result the TTL is
dead; tests must assert stale-marker → block AND that a re-touch restarts the
window. Also mtime-based TTL means any process can extend the window by
touching again — intended for solo sessions, but exactly the parallel-session
leak from challenge 1. Confidence "session can create marker": HIGH.
Confidence "expiry enforced": HIGH only if the stale-marker test ships in T1.

**Eisenhower placement:** Important + Urgent (Do now). High damage class
(shared-hub recovery deadlock requiring human terminal intervention),
fresh incident, low implementation cost (standard complexity). Borderline
Schedule on raw frequency (rare), but the fix is cheap, context is current,
and #203's auto-sync recovery assumes an operator path exists for the
non-auto class.

**Align decision:** CONDITIONAL GO — build the TTL'd file marker as
specified, with three conditions folded into the Scope gate:

1. **Parallel-session leakage:** resolve in the design — session-scoped
   marker (record creating session id, guard matches it) OR explicit
   documented acceptance of machine-wide-within-TTL + audit log. The
   issue's I3 claim "never applies to parallel sessions automatically"
   must be corrected either way.
2. **Concrete README deliverable:** name the actual doc file (create
   `extensions/main-worktree-guard/README.md` or extend an existing doc)
   and add drift-guard source assertions for the doc/skill claims.
3. **TTL semantics pinned:** mtime-based, touch-refreshable, default 15 min
   as a named constant, env-overridable or not decided; T1 gains the
   stale-marker (expired → block) and refresh (re-touch → allow) cases.

Alternatives considered: (a) pi-native command — rejected (unproven
extension surface); (b) single-command whitelist — viable fallback;
(c) env-only (status quo) — rejected (incident cause).

## Stage 1 — Align (standalone, adversarial-lite)

### O/I/T alignment check

**Objective** — "Make task dispatch fail fast and resumably when a sub-agent is
cut; the parent currently blocks ~6h on dead task calls and orphan processes
survive the watchdog cut." Coherent and action-oriented.

**Indicators** — check each for measurability:

1. *Partial results + cut reason < 60s after cut.* Partially measurable as
   written. The current heartbeat kill path (builtin-tools `spawnSubAgent`)
   already resolves promptly (≤10s cadence) with `killed: true, reason: ...`
   + partial stdout/stderr for the internal kill clauses — so "cut reason"
   exists. **Gap:** the dominant failure class (tools in flight at cut time)
   cannot be detected in 60s by any current clause: `toolsInFlight > 0` +
   `turnActive` latches the tool-stall exemption, so the only firing clause is
   tool-stall at 6h; and a cut that leaves the child hang-but-alive (PID 6632
   sat at 0% CPU) is invisible to exit-based detection entirely. "Cut" must be
   defined operationally (process death vs liveness loss) before the 60s
   target is testable — scope/research must pin this.
2. *Orphan sweep — 0 orphan pi children after a wave of 3 cuts.* Testable via
   smoke `ps` anchored to the dispatch's process group. Feasible: the heartbeat
   kill path uses plain `proc.kill("SIGTERM")` (NOT `treeKill` — unlike the
   subagent extension #137 and the exit watchdog #153) — a forked child holding
   the stdout/stderr pipes both survives the cut AND blocks the parent's
   `close` event (the 6h mechanism). `shared/tree-kill.ts` precedent exists.
   **Gap:** sweep scope needs a safety anchor (see Challenge B) — "sweep"
   must be group/ancestry-anchored, not a generic pi-wide kill.
3. *Orchestrator guidance — assume-dead + resumable in `parallel-orchestrator`.*
   Measurable via config-validation source assertion. Verified today: the skill
   has a Partial-Failure Handling section but zero assume-dead/commit-early/
   re-dispatch guidance. Gap confirmed real.
4. **Missing indicator:** the Objective says "resumably" but no indicator or
   target exercises the resume side (re-dispatch on cut, commit-early
   contract). I3 covers guidance only. Acceptable at standard complexity, but
   the resume contract should be named in I3, not just "assume-dead".

**Targets** — "Simulated cut → partial results < 60s" and "no blocks beyond
watchdog bound + margin". Coherent; note the 6h tool-stall bound is a
deliberate ceiling for genuinely long tools (deploys) — the target is that a
*cut* returns at bound-latency, not that the bound shrinks. Keep tool-stall at
6h; do not "fix" this by lowering it (Challenge A).

**O/I/T verdict:** sound in intent; two measurability gaps to close at Scope
(operational definition of "cut"; sweep anchor) — both satisfiable.

### Adversarial challenge A — "Is the 6h block a symptom, not a bug? Would lowering bounds suffice?"

Strongest case: the 6h block is just the tool-stall bound doing its job when a
child is cut mid-tool, and the orphan problem is just `proc.kill` vs
`treeKill`. The minimal fix is two small changes — (1) settle the parent's
spawn promise on process `exit` (fires on child death even when an orphan
holds the pipes open) in addition to `close`, and (2) `treeKill` instead of
`proc.kill` on every kill path — plus a 6h→30min tool-stall bound. That would
resolve today's incident class without any new watchdog, sweep, or doc work.

Why it does NOT suffice (PROCEED): (a) lowering tool-stall to 30min reintroduces
the #489 class — killing productive agents mid long tool (deploy, batch reads);
the 6h bound exists because real tools exceed 30min. (b) Exit-event detection
fails for the hang-but-alive cut mode (0% CPU orphan FORK observed — the child
itself may survive a provider-side cut), so a liveness-gap detector (fast
marker deadline: ticks flow every 30s → 2-3 missed = cut) is needed to meet the
60s target for the observed class. (c) The "cut reason" contract and the
assume-dead/re-dispatch guidance are what make dispatch *resumable* — without
them the parent cannot distinguish cut from done and cannot decide re-dispatch.
The issue is the parent-side contract + sweep, not a bound tweak. The two-line
fix is folded IN as the core; the rest is contract + detection + doc.

### Adversarial challenge B — "What assumption is this betting on that could be wrong?"

The central bet: **a cut is promptly and safely detectable**. Three sub-assumptions:

1. *"Cut = child process death, observable via exit/close."* Wrong for the
   observed 0% CPU case: if the harness cuts the provider/model request while
   the pi process hangs alive (event-loop wedge, #153 class; or a forked
   grandchild surviving), exit never fires. Medium confidence this is the
   dominant mode — PID 6632 was described as a "fork", implying a child of the
   child. Detection needs a marker-gap deadline, and that must be calibrated so
   it cannot fire on a legitimately busy-but-ticking agent (markers exempt
   working agents by design — #176 semantics).
2. *"The orphan sweep cannot kill legit processes."* Risky if the sweep is not
   anchored. A process-group anchor is safe (detached groups are unique per
   dispatch); a pid-list or "pi by name" sweep is not — it could match the
   orchestrator's own session or a sibling wave, and pids can be recycled.
   Must verify ancestry (ppid chain) and never touch the orchestrator's own
   group. Also: an orphan killed mid-write can leave `index.lock`/partial
   worktree state (ties to #195) — sweep must be paired with the existing
   worktree-recovery path, or the "no zombies" fix just shifts the mess.
3. *"Re-dispatch on cut is safe for stateful work."* Sub-agents in this
   pipeline write files (docs/plans, DB rows). Assume-dead + re-dispatch
   assumes idempotent-ish workers; a half-written doc clobbered by a re-dispatch
   is a plausible new bug class. The commit-early contract mitigates only if
   guidance is explicit about idempotency and partial-output preservation
   (result caching F6 exists in the subagent tool — reuse it).

Confidence: assumption 1 is medium-risk and directly gates the headline target
(60s); assumptions 2-3 are design constraints, satisfiable at Scope.

### Eisenhower placement

**Important + Urgent — Do now.** Same-day incident (2026-08-12 wave): every
watchdog cut on the dispatch backbone risks a 6h orchestrator block + leaked
processes holding worktrees/MCP pairs, and parallel dispatch is the fleet's
core concurrency primitive (codebase-audit, plan-review, epic-executor all fan
out). Reliability debt is bleeding today; the fix is small and
precedent-backed (treeKill + exit-event + skill doc). Not Schedule (incident

### Align decision

**Decision: GO** — conditions folded into Scope/research:

1. Research/Scope must pin the operational definition of "cut" (process death
   vs liveness loss) and confirm the dominant mode, because it decides whether
   the 60s indicator needs an exit-event resolver (small) or a marker-gap
   deadline detector (medium).
2. The orphan sweep MUST be group/ancestry-anchored with a defined exclusion
   envelope (never the orchestrator's own group; ppid-chain verification), and
   coordinated with #195 worktree recovery.
3. Keep the tool-stall bound at 6h (deliberate ceiling for long tools) — the
   target is parent-return-on-cut, not bound-shrink.
4. I3 must name the resume contract (commit-early + re-dispatch on cut +
   idempotency expectation), not just assume-dead.

**Alternatives considered:**
1. Lower tool-stall bound (6h→30min) only — rejected: reintroduces #489
   (kills productive long-tool agents); doesn't fix orphans or the resume
   contract.
2. treeKill + exit-event only (no sweep, no doc) — the core, folded in; alone
   it leaves the hang-but-alive cut class undetected and dispatch non-resumable.
3. Full re-architecture of task dispatch (dedicated cut daemon) — overkill at
   standard complexity; heartbeat machinery + treeKill + exit-event suffice.

**Key assumptions:**
- Cut is (mostly) observable as process death via `exit` — confidence: medium
  (0% CPU fork observed; provider-side cuts may leave children alive).
- Process-group anchoring makes the sweep safe — confidence: high (detached
  spawn + treeKill precedent #137/#153).
- Re-dispatch with commit-early + result caching is safe enough for this
  fleet's doc/file-writing sub-agents — confidence: medium-high (needs
  idempotency phrasing in guidance).

**Recommendation:** Proceed to Research (Stage 2) — targeted: confirm the cut
mechanism class (exit vs liveness), and confirm sweep anchoring against the
observed PID 6632 pattern. Standard complexity stands.

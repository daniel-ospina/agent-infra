## Confirmed Problem Definition

**The failover hop's availability predicate has no term for "this leg cannot authenticate", so a
latched primary advances pre-spawn onto a declared-but-unkeyed leg, and the dispatch dies naming a
provider nobody chose.**

Scope is the two-part unit **RC1 + RC1b**. RC1 alone is inert — see *RC1b* below.

### RC1 — the hop predicate is credential-blind

`unavailableProviders()` (`extensions/shared/provider-failover.ts:980`) → `blockedLegSet()` (`:950`)
is the union of exactly three sets: the env block list, durable auth blocks, and fresh
own-exhaustion records. **No credential term.** `nextLegAfter` (`:1024`) skips only on that set
(`:1055`), so a provider with no key and no models is a *fully available* hop target.

### RC1b — the obvious fix is inert, and this is the finding that decides the seam

The natural repair is to ask the existing credential helper at the hop site. **It would not work.**
`providerApiKeyEnvRef` (`extensions/builtin-tools/index.ts:772`) is built on `loadModelRegistry()`
(`:258`), which reads **only `models.json`** and never merges extension `registerProvider` calls.
Live `models.json` gives `openrouter` = `{modelOverrides: {...}}` — no `apiKey`, no `models` — so the
helper returns `undefined`, which `gateOffTableRequest` explicitly treats as *"pass through
UNCONDITIONALLY"* (`:812-818`). A hop predicate built on it would **not** skip openrouter, and this
exact incident would reproduce.

The correct oracle already exists on the extension context — **`ctx.modelRegistry.getProviderAuthStatus(provider)`**, the only member of the three that takes a **provider id** *and* is synchronous (F-9, Cycle 2 P2; **corrected again in Cycle 3** — `hasConfiguredAuth` is **also** synchronous, so synchronicity alone is not the discriminator): `getApiKeyForProvider` is **async** and routes through a **different** path whose live-read/short-circuit behaviour this artifact never analysed, and `hasConfiguredAuth` takes a **`Model`** and answers from the stale `snapshot.configuredProviders`. The task tool **does** receive `ctx` (`index.ts:4499`). The knowledge exists; the hop path consults it only for off-table asks (`gateOffTableRequest` `:798`, `altGateEligible` `:867`), never for hop targets.

### RC1c — the credential term is NOT a pass-through on the write side (found by the history reviewer)

The first three cycles treated `setExhausted` as gaining only a carried input. It does not. Its halt branch
passes the input straight into `nextLegAfter` and then PERSISTS the result, so a walk emptied **only** by the
credential term used to write `terminal: true`.

That mattered because the two persisted fields are read asymmetrically: `activeLeg` is re-validated against
the current `unavailable` set before it is served, but `terminal` is honoured **unconditionally and before any
re-walk**. So a halt caused by an *observation the oracle can retract* (a stale-snapshot `{configured:false}`)
became durable state for up to the 24h TTL. The halting session cannot clear it itself — resolution halts
pre-spawn, so that session produces no marker — and recovery therefore requires one of: a marker-driven write
from a dispatch that *does* run (another session or pane, whose own oracle has since retracted the verdict),
a clear of the root record — **poller or manual** (`clearExhaustion`, reachable via `manualClear` / the CLI
`--clear`) — or TTL expiry. (An earlier draft named only the poller; a reviewer pointed out the manual clear is
the same primitive.) (An earlier draft of this section claimed "no marker-driven write can
ever clear it" and called it self-sustaining; a reviewer FALSIFIED that by probe — a marker-driven write with a
retracted oracle does clear it — and the claim is narrowed here rather than kept.) That is an availability
regression of the same shape PR #1032 (#727) fixed for `activeLeg`, and it also narrowed the T4 residual's
"contained by failing loudly" claim from *per-resolution* to *for up to a day*.

Fixed by making the credential term unable to set `terminal` on its own: the halt branch re-walks **without**
the credential term, and a leg found that way means the oracle alone emptied the chain — so the write records
`terminal: false, activeLeg: null` and the next resolution re-walks against a fresh oracle. Both directions are
pinned by tests (the durable shape, and the recovery once the verdict is retracted).

## Phase 1.5 — Axis Research

> **Trigger:** Architecture = medium+ (fires); UX=low, Ontology=low; no third-party dependency added.
> **Outcome: FIRED.** An initial justified-skip was ruled invalid by problem-verify (Cycle 1, F-3) —

> 8 searches / 6 primary-source fetches, no gated models. Brief: `#issuecomment-5873056079`.

**Load-bearing finding — the ecosystem runs TWO gates and we have one.** Kubernetes readiness ("controls
whether a Pod receives traffic"; Services do **not** fall back to unready Pods) and Envoy active health
checking (a failed host is "excluded from load balancing") are an **eligibility precondition on selection**;
observed-failure ejection is the second gate. `unavailableProviders()` is entirely the second kind. That gap
is a recognised pattern, not an invention.

**The counter-case, taken seriously and still live.** The real defect may be the **missing failure signal**,
not the credential-blind predicate — a dead leg that surfaced as a failure costs one attempt, not a
30-minute outage. Credential-gating is then an optimisation layered on a defect it does not fix, and it can be
wrong in the **other** direction (a stale verdict removes a *usable* leg). Supporting facts: Envoy and
Kubernetes explicitly disagree about each other's state; a 429 is routinely surfaced as
`"Authentication error"`; keys are hot-reloaded (absent at selection ≠ absent at call); and
**presence ≠ entitlement**.

Recorded, not settled: no LLM gateway documents credential-presence as a *selection* precondition, so this fix
would be ahead of documented practice in that layer while matching the load-balancer/health-check layer. **An
earlier claim in this artifact is retracted: that credential-gating is *the* fix. It is one of two gates.**
The alternative the evidence does **not** rule out: a **config-time hard failure** (refuse to start when a
declared leg has no key). **Kept as a live option for Phase 3. Adoption gate: no recorded decision is
contradicted.**

## The oracle is a LIVE read and is safe (settled from source, `@0.85.1`)

A **cached** verdict would make the fix actively harmful, so this was settled from the pi source rather than
assumed. Trace: `#issuecomment-5873322759`. `getProviderAuthStatus(id)`
(`dist/core/model-runtime.js:411`) resolves in order: `credentials.hasRuntimeApiKey` (LIVE) →
`snapshot.storedProviders` (SNAPSHOT) → `configuredRequestAuthStatus(config, extensionProviders.get(id))` →
`snapshot.auth` (SNAPSHOT).

Step 3 is decisive. `configuredApiKey = extension?.apiKey ?? config?.apiKey` — **the extension provider is
read first**, which is exactly what `loadModelRegistry()` (models.json-only) cannot see. That is RC1b's
mechanism. For an env-var-declared key it calls `isConfigValueConfigured` → `resolveEnvConfigValue(name, env)
= env?.[name] || process.env[name]`, evaluated **at call time** — a live read. It returns
**`{configured: false}`**, a *truthy object*, so `if (configured) return configured;` **short-circuits and does
not fall through** to the stale snapshot (`undefined` is the fall-through signal; `false` is a verdict).
**The openrouter case — declared `$OPENROUTER_API_KEY`, env var absent — is therefore answered live and cannot
be masked by a stale snapshot.**

**Residual (bounded, disclosed).** A provider declaring **no** apiKey (OAuth/ambient) returns `undefined` at
step 3 and falls through to the possibly-stale step 4, where a stale `{configured:false}` could wrongly exclude
a usable leg. Both paths return `{configured:false}` with no `source`, so they are **indistinguishable through
this API**. **Contained by failing loudly, not eliminated** — and "loudly" now means *observable to a
program*, not only to a reader: the `tool_result` hook marks a failover halt, a watchdog cut and a spawn
error `isError: true`, so an over-skip that ends in `failoverHalt` surfaces as a **failed dispatch** rather
than a silent success (before that extension, only the spawn error did — a cut recorded `exitCode: 0`).
Recorded as an accepted residual (T4).

**T6 (P3 — disclosed by the cycle-4 verifier, deliberately NOT fixed: a different class from T1).**
`interactiveRestoreTarget` (`provider-exhaustion.ts:167-181`) returns `familyLegs(fam)[0]` without consulting
`unavailableProviders`, and its call site (`:584`) passes no set. It returns non-null only when the family's
root record is **absent** — i.e. no latch — and that state is `resolveWithChain`'s `clear` early return, which
hands back the *requested* leg verbatim without consulting `unkeyed`. So a restore does pass through
credential-blind. **That is not the T1 class and is deliberate:** T1 is a *latched primary advancing onto an
unkeyed alternative*; this is the *root of an unlatched family being dispatched at all*, which is byte-for-byte
the cold-start path. Gating the root here would mean a provider the registry reports unkeyed could never serve
— including the ambient/OAuth providers that return `{configured:false}` without being unkeyed (the T4
false-negative), so the gate would refuse a usable leg. Left unfixed and recorded.

**T6b (P2 — found by the two-pass bug reviewer, deliberately NOT gated: the same ROOT class as T6, a weaker
instance).** The interactive **hop-own-drain root switch** selects `familyLegs(fam)?.[0]` without consulting
the predicate. `switchModel` is **not** a credential check — it resolves the target with
`ctx.modelRegistry.find(...)` (existence) and applies `pi.setModel`, reporting `false` when either fails; its
notice text says "no configured auth" but the condition it tests is resolvability plus `setModel`'s return. So
this site can move a session onto a provider the registry reports unkeyed. It is a **weaker** instance of T1
rather than the same one: it selects the family ROOT (the cold-start leg, which an unlatched resolution hands
back verbatim) and it is an interactive session switch, not a dispatch — and the DISPATCH path is gated
even from that state, because an unkeyed *alternative* is excluded by the predicate. Gating the ROOT would
refuse the ambient/OAuth providers of T4, i.e. refuse a usable leg, so it is recorded rather than fixed.

**T7 (P2 — PRE-EXISTING, surfaced by the history reviewer, NOT introduced here and NOT fixed in this PR).**
RC1c's fix makes the credential term unable to persist `terminal` on its own, but the *mechanism* the fix
names — `terminal` short-circuits **without consulting** the freshly computed `unavailable` set (the set IS
computed, then ignored), with no re-validation — is
general, and two other exclusions the same predicate consults are equally retractable:

- a **durable auth block** (`blockedLegSet` / `markLegBlocked`, documented as "READ-side TTL-bounded …
  self-heal on key remediation"), and
- the **`PROVIDER_FAILOVER_BLOCKED` env list** (`blockedProviders`, whose re-enable is "config-only = remove
  from list").

A halt written while the only unavailable legs were excluded by either one persists `terminal: true` and keeps
halting after the condition is retracted — the same #1032/#546 contract violation (a write-side decision must
be re-validated on read once its condition recovers) that RC1c fixes for credentials and #727 fixed for
`activeLeg`. Verified by probe: with `qwen-tp` env-blocked and `openrouter` auth-blocked, `setExhausted` writes
`{activeLeg: null, terminal: true}`, and clearing the block leaves `resolveWithChain` halting.

**Reproduces identically on the pre-fix revision, so it is not a regression from this PR** — filed separately as
**#1520** (`bug(failover): a family's persisted terminal halt is never re-validated`) rather than widened into
this change. The correct general fix is to make `terminal` a **re-validated hint** the way #1032 made
`activeLeg` one: when `fam.terminal` is set, re-walk and halt only if the walk still halts.

## Framings, assumptions and boundary (F-4)

**Four framings were considered.** (1) *Bug* — a predicate missing a term; fix the predicate. (2) *Config* — a
declared-but-unkeyed leg is a declaration error; refuse at config time. (3) *Observability* — the real defect is
the missing failure signal; fix the ejector. (4) *Ownership* — a pre-emptive balance latch hopping at all is
the bug. **Chosen:** (1), scoped to RC1 + RC1b, with (3) brought in as **P0-B** and (2)/(4) demoted to closed
options (2 stays a live Phase-3 alternative; 4 is an owner decision — see *Deferred*).

**Assumptions.** `[validated]` the override and configured default **do** resolve correctly (`:4513-4516`) and
are then *replaced* by `resolveDispatchLeg` (`:4714`); `[validated]` the hop was pre-spawn **for this
incident** (`:4713-4716`); `[validated]` the oracle is a live read (above). `[unverified]` that the consumer
set of the predicate is exhaustive — **this is the assumption Cycle 3 broke**, and the mitigating answer is
the seam (one computation carried by a bag every consumer already threads), not a per-site enumeration.

**Boundary / stakeholders.** The dispatch surface (`task`) and every gate that depends on it: a silent
dispatch failure reads to a caller as a clean reviewer verdict. Boundary is leg *selection* on the dispatch
path — **not** the balance-latch policy, **not** the ledger schema.

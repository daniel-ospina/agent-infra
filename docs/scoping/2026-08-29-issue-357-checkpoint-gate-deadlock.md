# Scope: #357 — sequence-enforcer checkpoint step-gate deadlocks pi -p workers

> Issue: https://github.com/daniel-ospina/agent-infra/issues/357
> Date: 2026-08-29 · Tier: Standard · Branch: feat/357-sequence-enforcer-checkpoint-gate

## Confirmed Problem

The sequence-enforcer's checkpoint step-gate (`gate: checkpoint`, Enforcement A #5039) is **unsatisfiable and inescapable** for any worktree pipeline session that reaches it, and it has **never passed once in production**: 118/118 blocked, 0 allowed, 0 warn_blocked on `parallel_check_*` steps as of the 08-29 snapshot (all on 08-28, all mode:gate, all reason "none found" — verified in `~/.pi/agent/audit/enforcement.jsonl`; **a further live deadlock cluster of 20 real-path blocked entries appeared 21:54-21:58 UTC during this scoping session — counts re-verified at implementation, snapshot-dated**). Affected class: **worktree pipeline sessions** — only worktree SKILL.md reads activate the pipeline (#7487 main-checkout carve-out), so all pi -p workers (subagent-tool, task-tool, epic-executor) and any interactive session working in a worktree. When such a session lands on a checkpoint step, it is permanently stuck:

1. **Token contract is broken end-to-end (P0 root cause).** The token writer (`swarm/operations/coordination/parallel_work_check.py` `_apply_token`) writes `"ts": time.strftime("%Y-%m-%dT%H:%M:%SZ")` — an ISO string. The TS enforcer (`checkpointTokenOk`) does `Number(token.ts)` → `NaN` → always "stale". The swarm Python reader (`sequence_check.py`) does `float(ts)` → `ValueError` → always BLOCK. **A fresh, phase-correct, CLEAR token can never pass either reader.** The checkpoint gate shipped 2026-08-12 (#5039/#223) with this never-passable contract and zero token-acceptance tests.
2. **`token_phase` is dead code on the TS side.** The `Step` interface lacks `token_phase`; the frontmatter fallback parser in `loadSteps` extracts only 8 fields (name/type/skill/requires/produces/gate/retry/timeout_seconds). `checkpointTokenOk` reads `(step as { token_phase?: string }).token_phase` → always `""` → phase check never fires. The swarm `sequence_check.py` enforces phase strictly — divergent trust between the two enforcers.
3. **No in-session escape exists.** At a checkpoint step with a missing token, `validateToolCall` blocks EVERY tool (read/bash/task/subagent/web_search/todo_write/mcp_catalog/loop_enforcer/mcp_load). This violates the established #7470 guarantee ("loop_enforcer always allowed — the gate must never block its own escape hatch") — the audit shows `loop_enforcer` blocked 3 unique times in production (6 double-audited entries: 09:56, 16:12, 19:57). `gateGuidance()` also has an early-return bug (`if (allow.length === 0) return ""`) making the checkpoint guidance branch unreachable → blocked messages carry `allowed: []`, `hint: ""` — the worker gets zero constructive guidance.
4. **Token production is impossible in worker/single-session contexts** even if bash were allowed: `parallel_work_check` is not on worker PATH; workers lack GH_TOKEN, SWARM_CARD_ID/AGENT_ID, Supabase creds; C1/C4 start with `git fetch` inside a ~2s python budget / ~4s shell watchdog (cold fetch → UNKNOWN → token REMOVED); checkout_guard DEFERs on the session's own dirty tree → STALE. Parent-session probe reproduced: `C1: UNKNOWN git-fetch-failed` (watchdog) / `C1: STALE` (documented) → no token written.
5. **Mode resolution contradicts the documented default for a part of the pi -p fleet.** The enforcement skill documents "pi -p sessions default to warn". `resolveMode()` keys the print default on `isPrintModeEnv()` (env `PI_MODE=print` only), so sessions with the print flag in ARGV but no PI_MODE env resolve `gate`. All agent-infra/swarm spawners DO set both (subagent tool: `--mode json -p` + PI_MODE=print; builtin-tools task tool: PI_MODE=print; swarm_daemon: `pi -p` + PI_MODE=print) → their children correctly resolve warn. The gate-resolving classes: **bare-shell `pi -p`** (cron, manual, other-repo spawners) and **interactive worktree sessions** (no -p, no PI_MODE → gate default). [inferred-not-audit-proven: 08-28 startups ≈ 740 warn vs 54 gate (live log, snapshot; the shared JSONL grows continuously — itself evidence for the audit-session-id issue); gate class = small minority, consistent with bare-shell/cron/other-spawner — but the audit has no session attribution]
6. **Checkpoint steps have NO advancement semantics in ANY mode.** `stepIndex` advances only on human gates (`agent_end`), auto gates (read handler), and verifier gates (`tool_result`). A checkpoint step with a VALID token in gate mode unblocks tools but never advances `stepIndex` — the pipeline freezes at the step forever, all subsequent gates unreachable, bridge state stale → orchestrator restart loops. This is mode-independent; the gate is structurally a permanent freeze point even in its intended happy path.
7. **Observability:** ~⅔ of gate-mode blocks are audited TWICE (once in `validateToolCall`, once in the handler) → 125 parallel_check entries (118 production + 7 probe artifacts at 20:33:28) ≈ ~71 real events; audit entries lack session attribution (no pid/session id/argv). 08-28 startups: ≈740 warn / 54 gate (live log snapshot). Audit-file hygiene: probe/test harnesses that bypass the NODE_ENV=test audit sink pollute the shared production log (observed 20:33:28 during verification — entries with synthetic `/repo/skills/` paths and empty skill paths; those are NOT production events; the production count stands at 118 blocked / 0 allowed).

**Impact class (verified):** 2026-08-28 19:55–19:58 UTC batch of pi -p workers — one worker hard-blocked on every tool at `parallel_check_plan` (writing-plans) for ~72s until termination; 09:55 UTC commit-workflow class blocked too. Any worker (epic-executor, task-tool, product-verifier at PR time) that reads a checkpoint-gated skill deadlocks. Interactive sessions can hit it via commit-workflow's `parallel_check_implement` gate.

## Rejected problem framings

- **"Warn mode must audit-and-allow (issue direction 1)"** — already implemented in code; does not fix the deadlock (the victim resolved gate, and the stall is mode-independent — no advancement anywhere).
- **"Gate on the skill's phase instead of last-read skill's sequence (issue direction 3)"** — the enforcer has no phase model (tracks skills, not pipeline phases); `token_phase` parsing itself is broken; needs the contract fix as prerequisite and is the largest change surface with the least payoff vs the escape fix. Rejected with rationale: the gate is unsatisfiable independently of activation (contract + no advancement in any mode + no escape) — the "correct gate doing its job on a wrongly-activated skill" counter (Agent B) does not explain the interactive/worktree class where the skill IS being executed.
- **"Never block the token-producing tool" as a broad bash allowance (issue direction 2, literal)** — reopens destructive ops at the gate (S2 pre-mortem); must be a NARROW intent-scoped escape (command matches `parallel_work_check`) + loop_enforcer + read, never blanket bash.

## Falsification check

The confirmed problem would be falsified if: (a) a fresh CLEAR token with numeric ts passes the TS gate (contract works) — it cannot (NaN); (b) a worker can produce a CLEAR token in-session — it cannot (independent unsatisfiability layers, each reproduced/verified); (c) the gate has ever passed in production — 0 allowed events; (d) a checkpoint step has ever advanced in any mode — no stepIndex mutation path exists for it.

**Confidence: 92%** (all claims verified in code/audit/repro; residual 8% = session attribution ambiguity of the 08-28 audit (shared JSONL, no session id/argv) — flagged as a separate observability issue).

# Scoping — #386: background extensions (slack-bridge) duplicate + fight the owner lease across concurrent sessions

**Issue:** daniel-ospina/agent-infra #386 (feat, complexity:standard, Level: task)
**Date:** 2026-08-31
**Worktree:** `.worktrees/386-lease` (origin/main @ 1fcf668)

---

## Confirmed Problem

**On a memory-pressured machine with many concurrent pi sessions, the slack-bridge single-owner election (agent-infra #188) flaps: sessions frozen longer than the 90s heartbeat-staleness window get their lease stolen; when they thaw they discover the foreign pid, yield, and the WebSocket close funnels them into the 1s-base reconnect loop, which re-injects them into the election — producing lease ping-pong ("owner lease taken over by pid X" + repeated `reconnecting in 1000ms (fail streak 1)` churn).**

The observed evidence (#386 body, 2026-08-30):
- lease file owned by pid 53461 (34 h session); a session running #1894 logged `⚠️ owner lease taken over by pid 42990 — closing connection, re-electing` followed by repeated `🔌 reconnecting in 1000ms (fail streak 1)` — two sessions actively fighting.
- 20+ concurrent pi sessions; every session spawns npm children (≈5 GB total) → Jetsam kills (#385) → sessions freeze >90s (heartbeat lapses) → theft → thaw → re-steal.

### Double diamond — problem

**Diverge (framings considered):**

1. **F1 — Lease flapping under load (root cause).** The election lacks any re-election *grace*: a displaced owner immediately re-contends (30s recheck **plus** a 1s reconnect scheduled by `onclose` after the lease-lost close — two competing timers), and steals back as soon as the new owner's heartbeat also lapses (which it will, on the same pressured machine). Ping-pong is structural, not a fluke. *Evidence: socket-mode.ts 575–605 (yield) → 1382–1391 (onclose → `scheduleReconnect`) → 1454–1470 (1s backoff) → 1398–1452 (openSocket → re-acquire).*
2. **F2 — Dead owner not evicted (stale-lease visibility).** `pidAlive` = `kill(pid,0)` is a liveness probe, not an identity probe: it passes for pid-reused processes and zombies, so a genuinely dead owner can look alive and block takeover indefinitely. *Evidence: pidAlive 555–563; lease stores `startTime` (575+) but it is never validated.* (This is the "why a stale owner is not evicted promptly" question in the issue's Research Needed.)
3. **F3 — Duplication of extension work per session (memory pressure source).** Every session spawns npm children + runs ambient extensions; slack-bridge is one of several duplicates. *Not the #386 target:* the issue's O/I/T is entirely about the lease fight; the spawn/memory pressure is #385's domain (Jetsam). Out of scope — noted, not absorbed.
4. **F4 — Reconnect loop too eager for ownership-class failures.** The 1s base backoff is for *transient network* drops; it is misapplied to *ownership* failures (lease lost, claim blocked). A session mid-fight burns CPU/spawns at 1s cadence and stamps `apps.connections.open`. *Evidence: onerror/onclose 1364–1391 release + scheduleReconnect unconditionally (except the saturationTimer guard); the saturation path (771–785) is the correct model and the only one that suppresses the loop.*

**Converge — F1 + F2 + F4 (the lease fight is the root cause; F2 is a correctness gap in the same election; F4 is the churn amplifier).** Rejected: F3 (out of scope — #385 territory). The single fix surface is the election in `socket-mode.ts`; `repo-freshness.ts` has no lease (git's own locks guard it — confirmed by codebase explorer) and needs no change.

> F2 wording correction (verifier pass): a reused-pid/zombie owner delays eviction by at most the heartbeat window (90s), not indefinitely — the heartbeat-staleness path always fires. And dead pids are stolen at the next recheck tick (≤30s) today, not at 90s (90s is the heartbeat window). Corrected in the plan below.

**Falsification check:** If the fix works, 2 receivers sharing one lease file converge to exactly one connection; a displaced receiver never schedules the 1s reconnect and never steals back while the new owner's lease is fresh; an alive-but-frozen pid is NOT stolen until the (longer) frozen threshold, while a confirmed-dead pid is stolen within the existing ≤2 min window. Confidence: **85** (mechanism fully traced in code; no external-system dependence).

### Phase 1.5 — Axis Research (external, research-skill sub-agent, findings-date 2026-07-28)

> Trigger: Architecture axis rated medium (lease-fencing is a known distributed-systems pattern; no third-party deps; in-repo precedent #188). One focused query pass (4 questions, `sonar` Search API).

- **Fencing tokens** (Kleppmann, "How to do distributed locking"; Hazelcast FencedLock): fencing protects the *resource* from stale writers. Our equivalent: only the lease-holding pid may write the heartbeat; the existing `rec.pid !== process.pid` check in `refreshOwnerHeartbeat` is the right instinct. `[canonical]`
- **Displaced-leader grace** (k8s leaderelection: LeaseDuration 15s / RenewDeadline 10s / RetryPeriod 2s): a displaced leader must NOT re-contend until ≈ one full lease duration has elapsed since last observed renewal, plus jitter. **Scale to ~OWNER_STALE_MS (90s) + jitter — not a small fixed cooldown.** ⚠️ The 30s recheck already re-races at 30s; a shorter grace re-creates the same race. The 1s `scheduleReconnect` on the lease-lost close is the mechanism that re-injects the displaced session — grace must gate **election re-entry**. `[canonical]`
- **pid liveness pitfalls** (`kill(pid,0)` passes for zombies + pid-reused processes; real systems validate pid + start-time — Linux `/proc/<pid>/stat` field 22, macOS `ps -p <pid> -o lstart=`): lease already stores `startTime`; comparison is the missing piece. PID reuse is a live risk here (20+ churning sessions). `[pitfalls]`
- **Jitter on recheck polling** (k8s PR #101652 "Add jitter to lease controller"; AWS/Google retry guidance): N sessions on a fixed 30s recheck converge on the same takeover instant; jitter de-synchronizes. `[precedent]`

**Verdict:** all four design elements (a) displaced-owner grace ≈ lease duration + jitter, (b) longer staleness threshold for alive-but-frozen pids, (c) pid+start-time validation, (d) recheck jitter — supported. No contradictions.

### Double diamond — solution

**Diverge (approaches):**

- **A1 — Lease fencing (chosen):** (a) displaced-owner grace — on foreign takeover, set a `leaseLost` flag; `onerror`/`onclose` skip `scheduleReconnect` while set (mirroring the saturationTimer guard); re-elect once after ~ONE_LEASE_DURATION + jitter. (b) two-tier staleness — confirmed-dead pid (kill fails OR start-time mismatch) → next-recheck steal (≤30s, as today); alive pid with lapsed heartbeat (frozen, Jetsam) → steal only after FROZEN_OWNER_STALE_MS (~200s). (c) pid+start-time identity validation (macOS `ps -o lstart=`, Linux `/proc/<pid>/stat`, fallback kill-only) — treats pid-reuse as dead. (d) jitter on recheck/grace timers.
  - *Tradeoffs:* behavioral change to takeover latency for frozen owners (90s → 240s); tiny ps/proc shell-out per staleness check (bounded, cached). Best reliability/effort: fixes the ping-pong at its root, keeps ≤2 min dead-owner recovery, no new deps, single file + tests + README.
- **A2 — Designated-session gating:** elect one "designated" pi session per machine (e.g. first TUI), gate slack-bridge to it only. *Rejected:* requires new session-registry machinery beyond the lease file, breaks the "any session can recover" property, more complex than the bug warrants; the lease file IS the coordination primitive — stabilizing it is the root fix.
- **A3 — Config gating (AGENT_SLACK_BRIDGE_OFF / per-machine enable):** let users disable the extension. *Rejected:* a kill-switch, not a fix — default-on users still get the fight; adds per-session config divergence.

**Converge — A1.** It directly implements the issue's Research Needed ("lease fencing (re-election with grace), pid-liveness validation before stealing, or backoff") — all three, proportionally — with the best reliability/effort ratio, no new dependencies, and full testability with the existing assert-suite conventions.

## Plan (consolidated after verifier pass — P0/P1 fixes incorporated)

### Design decisions (verifier-mandated)

- **D1 — lease stores process BOOT time, not claim time.** `OwnerRecord` gains a REQUIRED `bootTime` field (ms epoch of the holder process). **`ownBootTimeMs()` derives from the SAME kernel-stored source as the identity probe — reusing the exported `parsePsLstart`/`parseProcStarttime` parsers on the own pid, cached once — so both sides of the ±2s comparison read the identical stored value and wall-clock steps (NTP) cancel; never `Date.now() - process.uptime()`** (a wall-clock-derived value shifts with the clock and would turn a healthy owner into an identity-mismatch wrong steal). Identity check compares the current pid occupant's boot time (`ps -p <pid> -o lstart=` with `LC_ALL=C` on macOS; `/proc/<pid>/stat` field 22 parsed after the last `)` + `/proc/stat` btime on Linux; ±2s tolerance) against the lease's `bootTime`. **Both the claim AND the 30s heartbeat refresh write `bootTime` from the cached `ownBootTimeMs()` and PRESERVE `rec.bootTime` on refresh (exact expression: `bootTime: rec?.bootTime ?? ownBootTimeMs()`, mirroring the existing `startTime: rec?.startTime ?? now` pattern at socket-mode.ts:597) — never a fresh `Date.now()`, never a dropped field** (a refresh that drops/resets bootTime would silently disable identity in production; typed REQUIRED so TS enforces it). Claim-time `startTime` is preserved for display/compat but NEVER used for identity. Old leases without `bootTime` → identity unverifiable → frozen tier, never an aggressive steal. *P1 (cycle-2 verifier A issue 1 / verifier B issue 1): the non-yield refresh reconstructs the record from scratch — an unwritten bootTime contract would poison every lease ≥30s old; P2 (cycle-6 verifier B): a wall-clock-derived ownBootTimeMs reintroduces the wrong-steal vector.*
- **D2 — `leaseLost` clear contract pinned to acquire-success.** `openSocket` clears `leaseLost` + cancels `displacedReelectTimer` at the single point `acquireOwnerLock` returns true, BEFORE `connectSocket`. `stopSocketModeReceiver` also resets both. Guard placement: `onerror`/`onclose` return early when `state.leaseLost` (safe: leaseLost=true always pairs ownsLock=false). *P1 (both verifiers): clearing only on connect leaves a session silently stuck (no lease, no reconnect, no recheck) when the post-acquire connect fails, and a stuck flag on the acquire-failure path.*
- **D3 — hold the lease across transient drops, bounded against flapping.** `onerror`/`onclose`/openSocket-failure paths release the lease ONLY when `state.consecutiveFails >= LEASE_HOLD_MAX_FAILS` (3 → released after backoffs 1s+2s+4s ≈ 7s), plus the existing saturation/yield/stop releases. This closes the lease-free steal window for ALL sessions (skippers included), not just displaced ones, while preserving #189's no-starvation property (a wedged session releases within ~7–15s). **Flap bound (cycle-3 verifier B P1): the hello handler resets `consecutiveFails = 0` UNCONDITIONALLY today (socket-mode.ts:1317-1320) — a connect→hello→instant-drop flap would never accumulate to the release threshold and would hold the lease forever (a regression vs today's release-at-streak-1 which let the machine converge). Fix: hello resets the streak only when the PREVIOUS connection survived ≥ `minStableConnectMs` (new injectable threshold, default `HEARTBEAT_MS`, tracked via a `connectedAt` timestamp stamped on hello). A flapping owner then accumulates streak 1→2→3 across drops → releases at ≥3 (~7s) → backoff grows 8s→16s→…→60s, opening re-claim windows for other sessions' rechecks → machine converges to a stable owner. A genuinely stable connection (up ≥ 30s before the drop) still resets normally.** *P1 (cycle-3 verifier B issue 1).*
- **D4 — yield schedules ONLY the grace timer (no 30s recheck).** The grace callback mirrors the `wantRunning && !ownsLock && !saturationTimer` guard; a successful re-acquire cancels the grace timer before connecting (no duplicate WS). *P1/P2: double-armed timers opened a second live WS in the common dead-new-owner recovery.*
- **D5 — thresholds injectable for tests, getter-level env fallback.** `frozenOwnerStaleMs`, `displacedGraceMs`, `leaseHoldMaxFails`, `minStableConnectMs` resolve at CALL time as `state.<x> ?? process.env.SLACK_SOCKET_<X> ?? default` — mirroring `ownerLockPath` exactly (socket-mode.ts:537-539) — via `startSocketModeReceiver` opts + env. Getter-level resolution (not receiver-start) is required because Test 32 builds a BARE state and calls `acquireOwnerLock` directly (no receiver): the tests set env vars (`SLACK_SOCKET_FROZEN_STALE_MS`, `SLACK_SOCKET_DISPLACED_GRACE_MS`, `SLACK_SOCKET_LEASE_HOLD_MAX_FAILS`, `SLACK_SOCKET_MIN_STABLE_CONNECT_MS`) before the bare-state calls and before `startConnected` — no `startConnected` signature change. **Env hygiene is mandatory per block: every injection site snapshots + restores its vars (the `TASK_LOAD_SCALE_OFF` precedent at socket-mode.test.ts:77-83) — plain `delete` also wipes a pre-existing ambient value — and the suite-top deletion loop gains the four `SLACK_SOCKET_*` names. (Cycle-6 P1.)** *P1 (cycle-1 verifier A): 90s/240s untestable in real time without injection; P2 (cycle-3 verifier B): opts-only injection would leave the bare-state frozen-tier assertions default-constant-coupled.*
- **D6 — pid probe hardened + cheap.** Own boot time computed once + cached. Foreign-pid probes memoized (pid → bootTime) with a 30s TTL (matches HEARTBEAT_MS); on a memo-hit where the heartbeat is already past the staleness threshold, re-probe fresh (bounded ~30s worst case otherwise). **Zombie detection is FOLDED INTO the boot probe** — one `execSync` parses both the zombie state (Linux /proc field 3 == `Z` / macOS `ps -o state=` == Z) AND the boot time (field 22 / `lstart=`), memoized under the same TTL (a zombie appearing mid-TTL delays eviction ≤30s — same bound the identity memo accepts). Probe uses a load-scaled timeout — **the load value is computed ONCE and passed explicitly to `loadScaledTimeoutMs` (reusing `getSystemLoad` per probe would double the blocking shell-outs per check)** — plus `LC_ALL=C`; timeout/unparseable → identity unverifiable → frozen tier. *P2 (cycle-1 verifier B issues 5–6 + cycle-3 P4): per-check shell-outs × 20 sessions would amplify the exact pressure the fix targets; a compare/tolerance bug would misclassify live owners into a new ping-pong.*
- **D7 — indicator re-scope.** The 24h "zero takeover lines" indicator is not achievable by design (every freeze-thaw logs the displacement line); the achievable target is churn-based: zero 1s reconnect bursts after displacement, zero re-steal while a fresh owner holds the lease, recovery ≤ ~4 min for frozen owners / ≤ ~2 min for dead owners. Flagged as dependent on #385 in the PR body. *P2 (verifier A): an unachievable indicator would false-fail a correct fix.*
- **D8 — misc:** reset `consecutiveFails = 0` at displacement (fresh backoff after grace); jitter (±~30%) on recheck + grace timers; skip-log prints the actual jittered delay; `SocketModeState` literals in the test suite updated for the two new fields.
- **D9 — single choke-point for reconnect suppression (cycle-2 verifier B issue 2).** `scheduleReconnect` itself returns early when `state.leaseLost` (one guard covering the disconnect-envelope branch at socket-mode.ts:1327 AND the onerror/onclose/openSocket call sites — the envelope handler bypasses onerror/onclose entirely), and the yield path also clears any pending `reconnectTimer`. This makes D4's "yield schedules ONLY the grace timer" invariant structurally enforced rather than per-handler; the skip-log's jittered text doesn't affect Test 30 (asserts only the substring). Also: keep `state.ws = null` BEFORE the leaseLost/saturation early-return in onclose (mirroring the current order).

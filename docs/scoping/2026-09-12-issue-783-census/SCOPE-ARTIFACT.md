## Phase 2 — Confirmed Problem Definition

**A `task` dispatch that has demonstrably done work and is then killed by the 6-hour wall-clock cap returns nothing the parent can act on — the result payload carries no *child-specific* location (no worktree, branch, HEAD or dirty state), no record of what the child was doing, children are spawned with `--no-session` so no transcript exists on disk, and the `task` path writes no durable outcome record — so the parent must reconstruct by hand where each run stopped, and up to six hours of accumulated progress knowledge is lost.**

> **Wording corrected in cycle 6.** This sentence previously read "carries no location", which the artifact's own table contradicts: **82/144** payloads name a repo root. That root resolves from the child's *spawn* cwd (`git rev-parse --show-toplevel` of it, so it is the enclosing repo's top level) — which `spawnSubAgent` forces equal to the parent's (`:2306`) — so for the live parent it is not new information; but it *is* information, and calling it "no location" was the same overstatement class the stderr rows exist to fix. The claim is now precise: **no child-specific location and no git state.**

## The retention contract (named, because the transcript choice depends on it)

The transcript option was chosen over heartbeat-only *because* it enables resume, and it is affordable **only** with a retention contract. Rev 1 asserted "delete-on-success + prune in scope" while naming no mechanism, owner, bound, or trip. That is fixed here:

| Element | Decision |
|---|---|
| **Location** | A dedicated child-session root via `--session-dir` (e.g. `~/.pi/agent/task-sessions/`), **never** the interactive session dir — keeps `/resume` clean and makes the whole tree prunable as a unit. |
| **Max age** | Failed/capped child sessions pruned after **N days** (default 7, env-overridable). Successful children deleted immediately. |
| **Max size** | Hard cap on the tree (default **2 GB**, `TASK_SESSION_MAX_BYTES`); on breach, oldest-first prune. **Arithmetically consistent only because the retained set is failed/capped children only** (delete-on-success): at ~650–1,410 dispatches/day, retaining *every* child would be 2–3 GB/day; retaining only abnormal exits at a 7-day horizon sits far inside 2 GB. |
| **Trigger** | A **NEW** artifact, not the #469 job: `scripts/pi-task-session-prune.sh` + `templates/launchd/com.eldato.pi-task-session-prune.plist` (hourly, dry-run default, farmed copy, `install-launchd.test.sh` coverage). **#469's `pi-reap-idle.sh` reaps *processes* gated on JSONL last-activity under `~/.pi/agent/sessions`; it does not prune files and its probe is scoped to the interactive dir** — it is a *pattern* to reuse (age gate, dry-run default, fail-closed), not a drop-in. Bounds named: `TASK_SESSION_MAX_AGE_DAYS` (default 7), `TASK_SESSION_MAX_BYTES` (default 2 GB). |
| **Orphan handling** | Delete-on-success **cannot** cover parent death, dispatch crash, or the parent exiting after a cap. The sweep is therefore the *primary* reclaimer and delete-on-success is only an optimisation — the age/size prune is what bounds the tree. |
| **Ownership** | Named role: the organisation-design-team operator on call for agent-infra (same owner as the #469 reaper), recorded in the plan and in the `AGENTS.md`/skill contract note. |
| **Sensitivity** | A durable, always-on transcript store can contain secrets echoed into child commands. Decision: the child-session root is created mode **0700**; that is a *mitigation, not a solution* — transcripts may still contain sensitive command text and model output. The honest position: this is accepted for a single-user machine with the root under `~/.pi/agent/`, and the storage decision is **revisited if the ledger (#796) or any shared/remote consumer is ever pointed at it**. (Cycle-3 finding: the contract previously said nothing about sensitivity while treating `git add -A` as a leak risk.) |
| **Trip** | **Corrected in cycle 2 — rev 2's trip could never fire** (prune-before-alert at the same bound resolves the condition before it can be observed). Revised: the prune is a plain **enforcement**, and the *observable* signal is a **prune event** — the sweep logs `[task-session-prune] freed=<N>MB remaining=<N>MB pruned=<N>` to a dated log, and emits a loud warning when it frees **anything** (a non-empty prune means abnormal exits are accumulating). There is no pager and none is claimed; the sink is the sweep's own log plus the next session-start health check. |

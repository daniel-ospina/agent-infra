## 1. Problem statement

The parallel-check checkpoint pipeline is single-tenant (swarm) by construction: checker verdicts/token contract, enforcer path wiring, and gate semantics all assume the swarm board, so C1–C5 cannot pass for no-board consumer repos. The fix makes C1–C5 passable for no-board tenants via a narrow tenant predicate (skip iff ALL of `SWARM_CARD_ID`/`CARD_ID`, board URL+key, `SWARM_TOUCHED_PATHS`/`TOUCHED_PATHS`, `AGENT_ID`/`SWARM_AGENT_ID` are absent; fail-closed on ANY signal) with honest, audit-distinguishable skip semantics, gate-side repo binding, single-canonical distribution of checker+connectors+guard, and re-pointed paths — one PR.

## 2. Approach selection: Card A — Predicate-in-checker ("writer-side skip, gate consumes")

Why A over B and C (evidence-mapped):
1. **A is the only card that satisfies the binding scope's exact wording.** Q15 + the problem-verify amendment pin "verdict detail carries a `no-board-skip` advisory" AND "skip semantics distinguishable in the token/verdict contract". A delivers both (advisory in the verdict line + `mode:"no-board-skip"` token field). B delivers neither (audit-only; direct checker runs still deadlock no-board). C changes the verdict set and breaks the vendored-distribution model.
2. **A fixes the working-tree partial's vacuous-CLEAR anti-pattern.** The 13-line partial (C3 `no-card-no-scope` CLEAR, C4 `no-card` CLEAR) writes byte-identical CLEAR tokens — the exact "never a byte-identical vacuous CLEAR" violation — and fires on `not card_id` regardless of board URL (a fail-open hole in board-configured sessions). A's refinement (predicate-gate + mode-flag + swarm-parity UNKNOWN for board-mode-no-card) closes the hole and restores swarm parity.
3. **Single-language predicate (Python)** — B requires a duplicated TS predicate with permanent cross-language drift risk.
4. **Additive, parse-safe contract** — verdict set unchanged (CLEAR/STALE/OVERLAP/DUP_FIX/UNKNOWN; sh header, sh wrapper pass-through, 33 tests, external consumers unaffected); token gains `mode` + URL-form `repo` (verified parse-safe: enforcer inline type reads only phase/verdict/ts). C's new SKIP verdict would exist ONLY in the vendored copy — permanent contract divergence from swarm upstream.
5. **Deploy window is a strict monotone improvement** over today's full deadlock, bounded by the #357 deploy-sync + md5 gate (see S2.5).

**Rejected alternatives — when they WOULD have been better:**
- **Card B (predicate-in-enforcer)** would have been better if the checker had to remain byte-identical to swarm HEAD (zero local checker patches — e.g., if the fix could be merged to swarm first and vendored as-is). It fails here because the fix-mandate requires checker-side C1 gating (direct runs must not deadlock), the binding pins the advisory in the verdict line (writer-side), and the two-language predicate drift is a permanent correctness hazard. *Revival condition:* a future scope drops the verdict-line advisory requirement or the checker becomes pure-swarm-owned.
- **Card C (SKIP verdict)** would have been better if the enforcer deployment lag were unbounded, or if non-enforcer consumers needed verdict-level distinguishability (e.g., a dashboard parsing verdict lines as the audit source of truth). Its fail-closed window is structurally safer if the deploy-sync + md5 gate ever lapses. *Revival condition:* the enforcer side ever needs contract-level distinguishability without token at-rest evidence.
- **S5 repo binding is separable** (Phase 5.6 P2 note): it closes a PRE-EXISTING adjacent hole (#378/#18393), not an O/I/T requirement; it was considered as a follow-up issue and rides on the contract-safety-hard rationale — skip-CLEAR tokens amplify cross-tenant leakage, so binding must ship with the skip. Recorded so a future reader understands the trade.

**S5. Repo binding — canonicalization PINNED: URL form, cwd-resolved, exact comparison, `"unknown"` sentinel; + first-class repo-path resolution fix.**
- **Canonical form:** `git remote get-url origin` (whatever git reports — URL or local path string), because (i) it matches the force-file contract already documented (enforcement SKILL.md L30 `repo: "<git remote>"`) — one comparison form for both token kinds; (ii) git worktrees share the common git-dir config, so the remote is worktree-agnostic and never mismatches between the checker and the enforcer; (iii) **the checker MUST use the same command as the enforcer's `currentRepo()` — `git -C <resolved> remote get-url origin` (trimmed) — NOT `git config --get remote.origin.url`**, because `url.*.insteadOf` rewriting applies to `remote get-url` but not `config --get` (empirically verified divergence; an insteadOf-configured machine would fail-closed every valid token otherwise). (Cycle-2 P3-1 fix.)
- **Resolution (fix, first-class task):** resolve the remote from the **checker's invocation cwd** — the same cwd the enforcer's `currentRepo()` uses, guaranteeing parity. Fallback chain for the git-OPERATIONS target: `--repo` → `PARALLEL_CHECK_REPO` → cwd → `_REPO_ROOT` (last-resort for non-git cwd). **The token-repo VALUE is decoupled from the ops target**: token `repo` = remote of the resolved ops target when that is a git repo, else `"unknown"` — it NEVER falls back to `_REPO_ROOT`'s remote (that would mismatch the enforcer's `currentRepo()` in a non-git cwd). (Cycle-2 P4-1 fix.)
- **Writer-side:** `GitOps.remote_url()` = `git -C <resolved repo> remote get-url origin` (fail → `"unknown"` sentinel, matching `currentRepo()`'s sentinel). `run_check` passes `token_repo` into `_apply_token` (replacing the raw `repo_path` arg).
- **Enforcer-side — CHECK-TIME binding via a MODE-AWARE token-state wrapper (Phase 7 H4-1 P1 + A2 ISSUE-1 P2 fixes — reconciled placement):** binding is evaluated inside the token-state computation — `checkpointTokenOk(ownerStep, {enforceBinding})` where `enforceBinding = (mode is gate/strict)` — so warn mode stays byte-identical (binding-free; wouldBlock/audit labels unchanged) and gate/strict evaluate `token.repo === bindingRepo()` after phase match. **The mode-aware result is consumed at ALL THREE gate/strict consumption sites** so the mismatch state is neither silent-pass nor silent-stall: (a) handler advance (`tokenState.ok` ~L1353-1395) — binding-fail → token NOT-ok path → checker re-run ALLOWED (fresh-token guard only fires on ok) + blocked-call reason names the repo mismatch; (b) `validateToolCall` checkpoint branch (~L926/L955) — binding-fail → blocked with the named reason, never "allowed-but-never-advancing"; (c) `gateGuidance` State-2 (~L805-809) — binding-fail shows State-1 + the run form + the named reason (never "already has a fresh token — do NOT re-run"). This is the reconciliation of the earlier S5/S12 contradiction (binding was written as "in `checkpointTokenOk`" AND "at the advance decision only" — both wrong alone; the mode-aware wrapper is the single uniform evaluation). **T8 gains a guidance/escape UX assert:** at binding-fail, State-1 is shown, the checker re-run is allowed, and the blocked call carries the named reason. `bindingRepo() = process.env.PARALLEL_CHECK_REPO || currentRepo()`. **Both-"unknown" pass is an explicit accepted limitation — worded for the full production surface (Phase 7 A4 ISSUE-1): no-remote OR NON-GIT-CWD contexts** (the checker's token-repo decoupling yields "unknown" for non-git cwds; the enforcer's `currentRepo()` does too) — symmetric with the force path; TTL + phase still enforced; T8 gains an unknown-unknown-pass vs unknown-vs-remote-BLOCK variant. **Legacy token fixtures (Phase 7 A1 ISSUE-1):** `writeToken` gains a default `repo: TEST_REPO` + `_setRepoForTest(TEST_REPO)` in the affected sections with the EXISTING per-test `finally { _setRepoForTest(null) }` reset idiom pinned at section level (process-global override — a forgotten reset cross-pollutes; mismatch cases write a differing repo via the `extra` param while the global override holds TEST_REPO) + ONE repo-less variant asserting the named-reason BLOCK. Legacy on-disk tokens (pre-fix abspath format) BLOCK with the named reason — TTL-bounded and diagnosable; re-run guidance covers it. **Asymmetric override cases (Phase 7 A4 ISSUE-2):** one-sided override fails closed BY CONSTRUCTION but is asserted: T8 gains (i) `--repo`-produced token + no enforcer env → BLOCK named reason; (ii) enforcer `PARALLEL_CHECK_REPO` set + cwd-produced token → BLOCK. **The earlier phase-start-capture idea is REJECTED (A1/A4 cycle-2 P1):** the enforcer is stateless (no "checkpoint becomes pending" event — pending is a checker-side token write the enforcer never observes; the token file is machine-global), so phase-start capture is unimplementable as written and was deleted. Check-time binding resolves the cd-mismatch class because **worktrees share the common git-dir remote** — cd to a worktree of the SAME repo still yields the same `currentRepo()` → pass; cd to a DIFFERENT repo → BLOCK (legitimate: the checkpoint is in B; a token written in A is stale). Enforcement L31 documents: "a token is repo-bound to the session repo (worktree-shared remote; `PARALLEL_CHECK_REPO` env honored; **a checker `--repo X` without the env binds X's remote — run the gate from X or a worktree of X, else the named-reason BLOCK**); a cross-repo BLOCK means re-run the checker in the current repo". Force path keeps the same check-time rule — symmetric.

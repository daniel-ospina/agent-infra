## Confirmed Problem

**The pass is not serialized against a shared `$STATE`.** Not "two processes exist" — the harm is
that two passes mutate one state dir concurrently, and the guard has to hold for **every** entry
point (launchd `StartInterval`, a manual run, `launchctl kickstart -k`), not just the scheduled one.

Measured, and reproduced on a clean restart so it is not a leftover:

| observation | measurement |
|---|---|
| two live processes on one `$STATE` | `2283 etime 04:55` beside `8835 etime 01:23` |
| kill the older one + `launchctl kickstart` the job | **two again within three minutes** |
| three coexisting | PIDs `56912`, `58371`, + a third arriving within minutes |
| the harm, while a downstream guard was absent | same-second **duplicate `spawn` for one `prd-` id** — 13 + 24 + 40 + 29 = **106** over 2026-10-21..24 |
| the harm since 2026-10-25 | **zero** — because `pr-doctor` gained its own "one worker per PR" guard, **not** because anything here changed |
| the remaining cost today | `pr-doctor` passes skipped — `04:53 → 05:04 → 05:22 → 05:53 → 06:23 → 06:26` (gaps 11/18/31/30 min against a 5-min cadence) |

Consequences stated, because they set the priority: the dangerous consequence is currently blocked
by a guard in a **different** component that nobody is obliged to keep, so this is **defence in
depth, not an active incident**. And it fixes the **versioned** script only — the live box runs a
drifted copy (1209 vs 1199 lines, 6 hunks), which is #1552 / #1738 / #1694 and is out of scope.

## Plan

Full plan: `docs/plans/2026-10-27-issue-2890-heartbeat-single-instance.md`.

A `mkdir`-and-stage lock directory at `$STATE/heartbeat.lock`, taken before the pass's first write
and released on exit, with **three independent correctness arms**:

1. **identity** — the lock records `pid` **and** the holder's own `ps -o lstart=` start time, and a
   contender defers only when **both** match, so a pid the OS recycled after a `SIGKILL` is
   reclaimed instead of silently stopping the box (#1985);
2. **age** — a lock older than `HB_LOCK_STALE_MIN` (30 min, the bound `$STATE/pr-doctor.lock` already
   uses) is reclaimed **even when its pid looks live**, because a pass cannot legitimately run that
   long (540 s target cadence, its own `STALL … exceeded 390s` killer) — a wedged holder costs one
   pass, never the box;
3. **one release point** — `TERM`/`INT` must **exit** (not merely return: `orch-loop.sh`'s #1715
   defect), so the `EXIT` trap is the only release and "the lock is gone" == "the process is gone".

Every constituent is a pattern already in the tree, not a new mechanism: `ai-drainer.sh` GUARD 1
(stage-then-`mv` claim, atomic `mv` reclaim, ownership-checked release), `$STATE/pr-doctor.lock` in
`heartbeat-loop.sh:768-793` (the `find -mmin +30` age rule), `watchdog-loop.sh` (the unwritable-
`$STATE` rule). Plus one new rule with no precedent: a debris sweep for `.heartbeat.lock.*` older
than the age bound — grepped, nothing else in the tree reaps that name.

### Adversarial Threat Surface

(not adversarial) — this is a mutual-exclusion guard, not enforcement code whose correctness is

### Decisions the issue left to this change

| decision | choice | reason |
|---|---|---|
| refusal exit code | **0**, not the issue's suggested non-zero | `scripts/lib/fleet-inventory.sh:68` renders a job's **non-zero last exit** as `FAILING`. At a 5-min interval against a 6–9 min pass, a second start while one is live is the expected, frequent, healthy case — a non-zero exit would paint the heartbeat `FAILING` on most ticks: a false red on the one component whose job is to report the box's state. The file's own header contract is "EXIT: always 0". |
| what a refusal writes | **nothing** under `$STATE`; reason on **stdout** | so a contended tick provably mutates no byte of the state dir. Trade stated, not hidden: a refused tick leaves no line in `orchestrator-heartbeat.log` (that log lives in `$STATE`). |
| unwritable `$STATE` | **permit**, loudly, on stdout | refusing would take the box's only alarm offline exactly when the box is broken — and could not even log why. Opposite arm to `watchdog-loop.sh` deliberately: there the guarded action is a RESTART and a never-advancing counter is the tight loop that file prevents. A pass cannot loop. |
| `--dry-run` under a live pass | claims if free, **never reclaims, never refuses** | a diagnostic must answer on a running box (`origination-funnel.test.sh` pins the same rule for `--check-refresh`). |
| `HB_LOCK_STALE_MIN=0` | **not a setting**; below 1 falls back to 30 | the bound is `find -mmin +N`, so `N=0` means "older than a minute" and a live pass at 60 s would be joined by a second — the #2890 defect re-created by misconfiguration. |
| `HB_LOCK_WAIT_S` default 10 s | bounded settle, **not** cadence | `kickstart -k` SIGTERMs the holder and starts the replacement immediately, and a trapped TERM only exits after the command in flight; without the settle the operator's repair verb silently does nothing. |

### Axis Research

**Axis: the canonical mutex for a shell single-instance guard.** `flock(1)` (`man7.org/linux/man-pages/man1/flock.1.html`)
is the standard answer on Linux — it wraps a command in a `flock(2)` lock on a file or directory,
and "a lock is automatically dropped when the file is closed". Attractive precisely because the
kernel reclaims it on death, so the stale-lock problem does not exist.

**Axis: why that answer does not transfer — and what the portable answer is.** `flock(2)`
(`man7.org/linux/man-pages/man2/flock.2.html`) is an **advisory** lock attached to an *open file
description*: it is released only when **all** descriptors on it are closed, it "does not detect
deadlock", and it is "not propagated over SMB" before Linux 5.4 (emulated since 5.5) — i.e. even
where it exists it does not answer *which process holds this*, which is the datum this guard has to
report on stdout and the reason the lock stores `pid` + start time rather than being anonymous.
And `flock(1)` is util-linux: **macOS does not ship it**, which on this box is decisive.

**Taken from the external pass:** it *confirms* the recorded decision below rather than opening a
new option — the anonymous-kernel-lock design and the portable directory-claim design are both
canonical, they differ by platform, and we are on the platform where only the second exists. It also
supplied the argument for keeping the **age** bound independent of liveness: an advisory lock's
only stale story is "the holder closed it", and where that story is unavailable, a bound in time is
the second opinion.

### Integration Docs

No third-party dependency — zero new deps, no version to verify. The external contract is the
platform's own userland, and it is pinned in the plan doc's `### Integration Surface Map`:
`ps -o lstart=` (not `/proc` — macOS has none), `find -mmin`, `LC_ALL=C` on both start-time reads,
and no bash-4 construct (macOS `/bin/bash` 3.2).

| S2 | `mkdir` claim + a bare `pid` file (the unadorned `pr-doctor.lock` shape) | **Rejected.** Liveness read from a bare pid is exactly the **#1985** defect: a recycled pid reads as "the holder is alive", which stops the box silently *and* blocks its own recovery — a start that defers to a wrong pid can never repair the lock it defers to. |
| S3 | **staged `mkdir` + `pid`&`lstart` identity + age bound + bounded settle** | **Chosen.** Three independent arms; every part a pattern already in the tree. |
| P3 | lengthen `StartInterval` so the pass fits the cadence | **Rejected as a fix.** Cannot cover a manual run or `kickstart -k` (the measured reproduction path), and still permits overlap. Cadence is an operator setting, not a correctness property. |
| P4 | close the live-copy drift instead | **Real, separate scope** — #1552 / #1738 / #1694. Changing the live box is explicitly out of scope for this PR. |
